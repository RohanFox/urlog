# Design Record: Agentless Log Investigation Platform

Nov 4, 2026 · @Rohan

## Purpose and scope

An open-source (Apache-2.0), agentless, post-hoc log investigation platform for CSIRT and incident-response analysts: the Splunk Search & Reporting experience, self-hosted, with no agents and no licence cost. Analysts upload evidence from Linux, Windows and application logs (web, mail) after an incident and investigate it interactively.

**v1 is interactive search.** An analyst must be able to find things unaided: type a query, filter by clicking values, pivot, bookmark, export. Detection rules are v1.1 and are not designed here.

**Users.** 1-3 analysts working concurrently on one deployment, each with their own investigations, with case-level sharing. Local accounts only.

**Agentless** means evidence is copied onto the machine running the tool, by web upload or SFTP drop. No collectors, no syslog listener, no remote pull in v1.

**Not in v1.** Real-time ingestion, alerting, dashboards builder, scheduled reports, detection rules, SSO/LDAP, clustering, PCAP.

## Scale, reference hardware and deployment

A small incident is about 50 GB of raw logs; a big one about 120 GB (2-4 systems, roughly one week). **Disk estimate (measured on the synthetic fixtures): 35-50 GB per 120 GB of raw logs, plus the original evidence files.** **nginx, measured on the evidence corpus (2026-11-11; 9.16 GB decoded, 24.3 M records of a 19-field custom layout, two hosts): 59 B/row on disk for 376-byte records, 6.4× (7.3× and 6.4× per host), the text index 12 B/row of it; 120 GB of such nginx is about 19 GB on disk.** The syslog figure below is fixture, not corpus (the corpus has no syslog files). A schema without per-column codecs measures 112 B/row for 223-byte nginx lines (2×), so the codecs were chosen from a per-column measurement: ZSTD(1) on every string, IPv6 and the Map, Delta on `file_offset`, T64 on the small integers, `message` an alias over `raw` instead of a copy, the eight most common extras keys as typed columns, LowCardinality Map keys. Result on the fixtures: 64 B/row for nginx (3.5×) and 57 B/row for syslog (2.4×), of which the text index is 12 and 23 B/row. Real logs repeat more than the fixtures, whose addresses, paths and agents are drawn from large pools: the corpus measurement confirmed it for nginx (above). `user_agent` stays `String`: on the corpus LowCardinality saves 1.4 B/row, 2.4 % of disk. The overall figure stays an estimate until IIS and EVTX, most of the corpus bytes, are measured.

| Item | Value |
| --- | --- |
| Reference box | 8 cores, 32 GB RAM, NVMe SSD, Linux |
| Concurrency | 1-3 analysts |
| Per-case raw volume | 50 GB typical, 120 GB large |
| Full ingest of 120 GB | 20 min at target, 40 min at floor |
| ClickHouse topology | single node, no replication or sharding |

**Deployment paths.** Docker Compose (backend + ClickHouse + reverse proxy) is primary and works on laptop, PC, VM or Docker host. A standalone Linux VM is supported with a .NET self-contained single binary, a systemd unit, and an install script that adds the official ClickHouse apt/rpm repository. No native Windows server install; Windows analysts use Docker Desktop or a Linux VM.

**Settings of one box.** The backend reads an optional `appsettings.Local.json` from its content root after the tracked `appsettings.json` files and before the environment (`ApiHost.AddLocalSettings`; `Urlog:LocalSettings` names another file, and an empty value turns it off). Git ignores the file and no build output carries it. It is where a development box keeps what is true of that box alone, such as a lower disk watermark on a small volume; a deployment sets the same keys through the environment, which still has the last word.

HTTPS is terminated by the bundled reverse proxy (Caddy or nginx, self-signed by default), not by the backend.

**ClickHouse memory cap.** Compose sets `max_server_memory_usage_to_ram_ratio` to 0.6 (≈19 GB on the reference box); the default lets ClickHouse take \~90 % of RAM and starves the backend's parse pipeline during ingest.

## Data model

`case 1→N host 1→N file`. The case is what analysts open, share and delete; the host is what they query; the file is provenance with its SHA-256. Every event row carries `(case_id, host_id, file_id, file_offset, parse_generation)`.

**Host resolution is per event, not per file.** Formats that carry a hostname (syslog, EVTX `Computer`, journald `_HOSTNAME`) resolve automatically; a forwarded-events EVTX fans out to several hosts from one file. Formats that do not (nginx, Apache, IIS, app logs) get the host at intake: inferred from the archive path or filename (`web-01/nginx/access.log.3`), proposed in the UI, confirmed or bulk-assigned by the analyst. Unassigned files are flagged, never blocked.

**Hosts after intake (`HostOperations`).** A person adds a host, renames it, sets its zone, gives it default source options and merges it into another host of the case. The default options are the options a file may carry (`nginx.log_format`), held once for the host in `hosts.source_options`: a parse reads the host's value for every option the file does not set itself, and intake scores a new file of the host against them, so the files of one host with a custom log format need no override each. A merge points the files of the merged host at the surviving one and keeps the merged row with `merged_into`. The row stays because events carry its id and SQLite hands the highest id out again once its row is deleted. Its name stays with it and leads to the survivor: a later upload under the old name lands on the surviving host, and no other host of the case can take the name. A merge parses nothing again. Every row keeps the `host` and the `host_id` it was written with, so both names are still found by a search. A rename, a zone and a default option do change what a parse writes, and the files they reach are parsed again (Cases, hosts, files and jobs API).

**Scope is strictly per case.** Hosts are created, matched and deduplicated only within the case the files were uploaded to. The same hostname in two cases is two unrelated host rows. There is no global host registry; cross-case search is a later feature.

**Case lifecycle.** `active → closed → archived → soft-deleted → purged`.

| State | Meaning |
| --- | --- |
| active | ingest and query allowed |
| closed | ingest frozen; query allowed; evidence cannot change after the report is signed |
| archived | the stored files in one `.tar.zst` with a hash manifest and the case's audit trail, under the archive root; ClickHouse partitions dropped; the case's directory empty; re-importable |
| soft-deleted | hidden for 7 days, recoverable; owner confirms by typing the case name |
| purged | partitions dropped, files deleted, metadata deleted; an administrator, or the schedule after 7 days. Never a stored state: the case's row goes with the last step |

**Transitions (`CaseLifecycle` in `src/Core/Metadata`).** The table is the whole set: close (active → closed), reopen (closed → active), archive (closed → archived only, never from active), soft-delete from active, closed or archived, restore back to the state the case was in when it was deleted (`cases.prior_state`; the close or archive time is kept), re-import of an archive to closed (evidence that was frozen stays frozen), purge only from soft-deleted (`purging` → `purged`, resumable by the reconciler; `purged` is the end of the purge and is never written, because the row of the case is deleted in the same transaction). Everything else, self-transitions included, is refused with both state names in the message; every `files` insert needs the case in active. Metadata ids are plain `INTEGER PRIMARY KEY` on SQLite and `bigint identity` on Postgres with no `AUTOINCREMENT`, so on SQLite an id can be reused after the row with the highest id is deleted (a purge of the newest case, then a create): audit rows name the case in `details_json`, not by id alone.

**Lifecycle operations (`LifecycleOperations` in `src/Core/Metadata`).** Each transition a person asks for is one transaction that checks the case under the write lock, changes it and writes its audit row. The times it writes (`closed_at`, `deleted_at`, from which the purge window is counted, `purging_at`, the times of a task) are read from the clock after the lock is held, like the times of a job. An operation carries out its own transition and no other one that ends in the same state: a close of an archived case is refused, although a re-import takes that case to closed, and a close or a reopen of a soft-deleted case is refused, although a restore may take it there. An actor with a user id is held to the role of the operation (`CaseLifecycle.RequiredRole`): close and reopen take an owner of the case, soft-delete and restore an owner or an administrator (`by_admin` in the row), purge an administrator. An actor without one is the operator on the box (`urlog case ...` without `--as`) or the tool itself. With `--as` the row names both: the account as actor, and the OS user that ran the command as `os_user`. The transition table by itself (`CaseOperations.TransitionAsync`, `CaseLifecycle.Apply`) and the setter of `cases.state` are internal to `src/Core`, so no route of the API can change a case's state without the role and the preconditions; a test in `tests/Api.Tests` fails if the API assembly can reach it, and a second one reads the API project's source and fails on a bulk update or delete on the cases set, a tracked write through it, or SQL that writes the `cases` table.

| Operation | Refused when |
| --- | --- |
| close | a job of the case is in `parsing`. Jobs still queued stay queued and are held, since the runner claims for active cases only; a reopen lets them run |
| reopen | the case has unfinished work |
| soft-delete | the name typed to confirm is not the case's name, compared exactly; a job of the case is in `parsing`; the case has unfinished work |
| restore | the case is already `purging`. A purge that was asked for and has not marked the case is withdrawn in the same transaction |
| purge | the case is not `soft_deleted`; a purge is already under way |
| archive | the case is not `closed`; a job of it is in `parsing`; the case has unfinished work. Carried out, it is given up when the case's directory holds an entry no file record accounts for, or the archive volume has no room for the whole of the stored files |
| re-import | the case is not `archived`; it has no committed archive on record, or that archive is `failed`; the case has unfinished work |

Archive and re-import take an owner of the case. Asking for either writes no audit row: `case_archive` and `case_reimport` name who asked.

Work that outlasts a transaction (a purge, an archive, a re-import) has a row in `case_tasks`: who asked, who confirmed, the step it is in, the hash of the backup, and for an archive its directory and the SHA-256 of its tar and of its manifest. While a case has such a row in `requested`, `running` or `committed`, close, reopen and soft-delete are refused; restore is the one exception named above.

What each state refuses:

| State | New files, uploads | Parse and re-parse | Query |
| --- | --- | --- | --- |
| active | taken | run | allowed |
| closed | refused, "case N is closed; only an active case takes files" (an upload: 409 at creation and at the next chunk; the bytes that arrived expire like any unfinished upload) | not queued, not claimed; queued jobs wait | allowed |
| archived | refused | refused, except the parses a re-import queued while that re-import is under way | nothing: the case is not in `SQL_allowed_cases`, also while it is being re-imported |
| soft_deleted, purging | the case answers 404 | refused | nothing |

**Purge approval and schedule.** Two-person approval is a configuration flag (`Urlog:Lifecycle:TwoPersonPurge`, `urlog ... --two-person`), off by default. Off: one administrator releases a purge, and a runner releases as `system` the purge of every case that has been soft-deleted for `PurgeAfter` (7 days). On: the first administrator leaves a request, a second and different administrator account confirms it, and nothing is purged on schedule; the 7 days only make a case due. Both steps are `case_purge_request` rows. The command line has one verb for both steps. The API has two routes, `purge` and `purge/confirm`, and the operation is told which is meant: asking never confirms a request that waits, so a second administrator who asks for a purge is told that one is waiting, and a confirmation is refused while the flag is off, when no request waits, and from the administrator who asked. The purge itself is under Consistency below.

**Disk accounting (`CaseAccounting`).** Per case: the bytes its intake records state for the files that arrived, the bytes under its directory in the evidence root with unfinished uploads counted apart, the bytes of its cache copies, the bytes of its archives under the archive root (what is left of an archived case, and kept after a re-import until a purge), and rows and compressed bytes in the event store from `system.parts` by partition. `urlog case usage` prints it; the case dashboard reads the same figures.

A configurable global disk watermark pauses ingest with a clear message instead of filling the volume.

## ClickHouse schema

One wide `events` table, never one table per case. Monthly partitions keep part counts sane at 1 M rows/s; the time predicate is served by `ts` in the sort key, not by the partition.

```sql
CREATE TABLE events (
  case_id          UInt64,
  host_id          UInt64,
  file_id          UInt64,
  file_offset      UInt64 CODEC(Delta, ZSTD(1)),
  parse_generation UInt32,
  ts               DateTime64(3, 'UTC') CODEC(Delta, ZSTD),
  host             LowCardinality(String),
  program          LowCardinality(String),
  severity         LowCardinality(String),
  event_code       UInt32 CODEC(T64, ZSTD(1)),
  event_action     LowCardinality(String),
  event_outcome    LowCardinality(String),
  user_name        String CODEC(ZSTD(1)),
  source_ip        IPv6 CODEC(ZSTD(1)),
  destination_ip   IPv6 CODEC(ZSTD(1)),
  process_name     LowCardinality(String),
  url_path         String CODEC(ZSTD(1)),
  http_status      UInt16 CODEC(T64, ZSTD(1)),
  msg_off          UInt32 CODEC(ZSTD(1)),          -- where the message starts inside raw
  msg_len          UInt32 CODEC(ZSTD(1)),          -- 0: the message is message_text
  message_text     String CODEC(ZSTD(1)),          -- only for sources whose message is not a byte slice of the record
  raw              String CODEC(ZSTD(1)),
  extras           Map(LowCardinality(String), String) CODEC(ZSTD(1)),
  http_method              LowCardinality(String), -- the eight promoted columns: extras keys until then
  http_version             LowCardinality(String),
  http_response_body_bytes UInt64 CODEC(T64, ZSTD(1)),
  http_referrer            String CODEC(ZSTD(1)),
  user_agent               String CODEC(ZSTD(1)),
  url_query                String CODEC(ZSTD(1)),
  syslog_facility          LowCardinality(String),
  process_pid              UInt32 CODEC(T64, ZSTD(1)),
  message          String ALIAS if(msg_len = 0, message_text, substring(raw, msg_off + 1, msg_len)),
  INDEX idx_msg lower(message) TYPE text(tokenizer = 'splitByNonAlpha')
) ENGINE = MergeTree
PARTITION BY (case_id, toYYYYMM(ts))
ORDER BY (case_id, host, ts);
```

The full list is `src/Core/Sources/EventColumn.cs` (the Native block layout) and the field catalog. Low-cardinality string fields are lowercased at ingest so `field=value` is a direct equality. **`message` is one logical column**: an ALIAS over `raw` located by `msg_off`/`msg_len`, with `message_text` as the stored fallback for a source whose message is not a contiguous slice of its record (a rendered EVTX event, JSON with escapes); `raw` is always stored and never aliased. The text index is built on the alias and `EXPLAIN` shows it used through it; `events_v` names its columns because `SELECT *` leaves an alias out. Decided on measurement: the copy cost 12 B/row on nginx and 12.5 on syslog, the offsets cost 2.

| Operation | Mechanism |
| --- | --- |
| Delete a case | `DROP PARTITION`, one per month the case spans; instant |
| Parse or re-parse a file | a new `parse_generation` per attempt, a lightweight `DELETE` before the insert and after the commit (below) |
| Hide uncommitted and stale rows | `events_v` shows only the committed generation of each file, from `file_generation` (below) |
| Timeline of a case | `case_histogram`: events per file, generation, severity and UTC minute, written before the commit of a parse and read through `case_histogram_v` (below) |
| Free-text search | `text` inverted index on `lower(message)` (GA since 26.2), tokenizer `splitByNonAlpha` (`default` is not a tokenizer name on 26.8); `tokenbf_v1` only as fallback on older servers |
| Re-parse concurrency | serialised per case |

**Parse or re-parse.** Every attempt writes a `parse_generation` no earlier attempt on the file used. Before the insert, a lightweight `DELETE` removes the file's rows of every generation except the committed one (what crashed or failed attempts left; skipped on a first attempt). After the commit, a second one removes the generations below the new one. Both carry `case_id` so they prune to the case's partitions. The committed parse is never deleted before its replacement is committed.

**Visible rows.** `events_v` filters `(file_id, parse_generation) IN (SELECT file_id, argMax(current, updated_at) AS visible FROM file_generation GROUP BY file_id HAVING visible > 0)` (migration 0006): the newest row per file of the \`file\_generation\` ReplacingMergeTree, which the backend writes on every commit. A file with no row, or whose newest row is 0, shows nothing, so a first parse is invisible until its commit, and so is a file whose hash has not been compared yet. The set is built once per query from a snapshot: a query sees one generation per file for all of its rows, whatever commits while it runs. SQLite stays the source of truth and the startup reconciler re-syncs the two.

Lightweight deletes are masks applied asynchronously and the mutation queue is sequential per table; the generation filter in `events_v` is what guarantees a half-finished parse or re-parse is never visible, and because a retry never reuses a generation, that holds whether or not a delete has applied. ClickHouse cannot read SQLite in the Compose topology, which is why `file_generation` is mirrored into ClickHouse. A dictionary over the mirror (`file_generation_dict`, reloaded after every commit, generation 1 for a file without a row) was rejected for two defects: uncommitted first parses were visible, and a reload landing while a query scanned gave that query two answers (measured: a `count()` in flight at a commit read 1,408 of 4,809,713 rows; a re-parse commit could mix generations in one result). Migration 0006 replaced the dictionary lookup with the per-query set and dropped the dictionary, its passwordless reader account `urlog_dict` and the write path's `SYSTEM RELOAD DICTIONARY` grant. Cost, measured on 25.2 M rows with the reference query `src_ip=X | stats count by url.path` (20 runs warm, three alternating passes): p95 206 / 217 / 212 ms against 200 / 205 / 206 ms for the dictionary form, median +3.4 %, p50 equal; `EXPLAIN indexes = 1` prunes partitions and the primary key on `case_id` and `ts` as before.

**Stored histogram.** The timeline of a case read from the events is a read of every row's time and severity. `case_histogram` (migration 0009) holds the same counts ahead of the question: one row per file, parse generation, severity and minute, the minute cut in UTC by the expression the search cuts its buckets with, in a plain MergeTree partitioned by case and ordered by case, file, generation and minute. A sum at read time adds the rows up; no engine folds them, because rows of two generations must never be merged into one.

*Filled* by one statement per parse attempt, `INSERT INTO case_histogram SELECT ... FROM events WHERE case_id = n AND file_id = f AND parse_generation = g ... GROUP BY severity, minute`, sent by the job runner after the attempt's last insert is acknowledged and its hash has compared equal, and before its commit. It counts the rows the store holds for the attempt, so the buckets cannot disagree with them, and it is no part of the insert path: no row passes through it on its way in, and the benches of the regression gate do not run it. The statement carries the least and the greatest time among the attempt's rows, which add nothing to the answer and let the read prune to the file's months and times. Every row is counted, whatever its time: an undated or a future-dated row is in a bucket as it is in `events`, and a range keeps it out of an answer as it keeps it out of a search. The statement is composed where every read of `events` is composed (`CaseScopedEventsQuery`, the case first), and a fill that fails fails the attempt like a failed insert, so a generation is filled once and nothing is counted twice. The case, the file and the generation are written into the statement as numbers and the rows are grouped by the two keys that vary, severity and minute. The server's bucket function returns a `DateTime`, which holds 1970 to 2106: a parse with a time outside that is not filled, a warning says so, and its case reads its timeline from the events. The alternatives were a materialized view on `events`, which puts a `GROUP BY` and a second part behind every insert block on the path the throughput figure is about and writes the buckets of failed attempts all the same, and counting in the client as batches pass, which counts what was handed over and not what is stored.

*Shown* through `case_histogram_v`, which filters on the allowed cases and on the committed generation of each file with the filter of `events_v`, word for word (a test compares the two migrations). The `file_generation` row that makes a parse's events visible therefore makes its buckets visible in the same statement. The buckets of an attempt that failed, of a parse that is not committed yet and of a generation a re-parse has replaced are in the table and hidden, as their events are. *Deleted* with those events: the two lightweight deletes of the re-parse protocol (before an attempt's insert, everything but the committed generation; after a commit, the generations below it) are sent to `case_histogram` with the same predicate right after `events`, so the hidden rows go when their events go, and as for the events nothing rests on a delete having been applied. Archive and purge drop the case's partition.

*Which cases have one.* The commit of a parse records on the file that its minutes were written (`files.histogram_generation`, in the commit's transaction). A file parsed before the histogram was kept has none until it is parsed again, and a case with such a file reads its timeline from the events: nothing is back-filled. `urlog ingest` keeps no file record and writes no buckets.

## Intake

Two paths deliver bytes; one integrity pipeline handles both. Evidence is read-only from the moment it lands, following NIST SP 800-86 and RFC 3227 practice.

**Web upload.** tus 1.0 at `/api/v1/cases/{caseId}/uploads` with the creation, termination, checksum and expiration extensions (`src/Api/Uploads`). The protocol is tusdotnet's (2.12.0, MIT); the bytes on disk are a store of the API's own, because the library's disk store verifies SHA-1 only and forgets an upload once its file has moved. A client sends 16 MB chunks, each optionally with an `Upload-Checksum` (`sha256`, or `sha1`, which the protocol requires a server to offer). A chunk goes from the request to the file through one 1 MB buffer, so the backend's memory does not grow with the file. The checksum is taken from the bytes on disk after the write, and a chunk that does not match (460) or that the client did not finish is cut back to where it began. Default limit 20 GB per file (`Urlog:Upload:MaxFileBytes`). Archives (`.gz`, `.zip`, `.tar.*`, xz, zstd, bzip2) are accepted; decompression happens in the parse pipeline, not at intake. No FTP.

*Who and when.* Owners and read-write members upload: a read-only member is answered 403, a non-member 404, as on every case route. An upload belongs to the user who created it and is 404 to everyone else, another member of the case included. The intake gate (below) is asked at creation, before a byte is accepted, with the declared length plus what the other unfinished uploads on the volume have still to send: a case that is not active is 409, a paused queue and a volume that would fall under its mark are 507, a length over the limit is 413. A case that is closed while an upload is under way takes no further chunk (409). The upload's metadata is checked at creation too, and a bad value is 400 with its key named: `filename` (required, at most 255 characters), `host`, `timezone` (a zone the box knows), `year` (1970 to next year) and `nginx_log_format` (a built-in name or a format that compiles), no control characters. Browser tus clients send keys of their own: `name` is the file's name when `filename` is absent, and `filetype`, `type` and `relativePath` are accepted and not used. Any other key is refused, so a misspelt hint is not lost silently. These become the intake hints; the uploader is the session's user. The request body limit is lifted for this route alone. The library would honour `X-HTTP-Method-Override`, which would let a HEAD, exempt from the CSRF check, act as a DELETE, so the route answers 400 to any request that carries the header.

*On disk.* Under `<evidence root>/<case id>/`: `.uploads/<id>` holds the bytes of an unfinished upload and `.uploads/<id>.json` what is known about it (length, metadata, user, expiry, state); `web/<id>` is the finished file. The id is 32 hex characters from the server. No name an uploader chose reaches the file system; the original name is a column.

*From the last chunk to the record.* The request that brings the last byte renames `.uploads/<id>` to `web/<id>` on the same volume and calls the intake pipeline, which does everything else: the hash, read-only, detection, the hints, and the record with its audit row and its job in one transaction. The upload endpoint adds nothing to that sequence, and its 204 means the file is recorded. When intake records nothing for the file (the case already holds the same bytes, or the file is a packet capture) no record points at `web/<id>` and it is removed, the one delete outside the uploads folder. The sidecar keeps the outcome (`done` with the file id, the SHA-256 and the job; `duplicate`; `rejected`; `failed`) until the upload expires, and `GET .../uploads/{id}` returns it, so a client that lost the answer to its last chunk asks HEAD, sees the offset equal to the length, and reads what became of the file. A process that stops between the last byte and the record leaves a complete upload behind; the next start and every sweep finish it, and a file that was already recorded is found by its stored path and not handed to intake a second time.

*A locked metadata file at the record.* The record is the last step of intake, and another writer may hold the metadata file when it is due. Intake then tries the record again under the policy the job runner's commit uses (`BusyRetry`, 60 s, `Urlog:Upload:HandOverBusyTimeout`): every attempt is a new connection and a new transaction, so the active-case check, the duplicate check and the audit chain head are read again each time, and the file is hashed once. A lock that ends inside that time costs the last request the wait and nothing else; it answers 204. Past it nothing was written and nothing is undone: the file keeps its name `web/<id>`, the upload stays `finalising`, and the request answers 503 with `Retry-After` and the problem type `upload-pending`. The upload is then handed to intake again every 5 s (`Urlog:Upload:HandOverRetry`) until it reaches a final state. The list of such uploads is in memory, holds an upload once, and loses it with the first hand-over that ends any other way; after a restart the sweep at start does the same work. Each of these later hand-overs hashes the file again, since no hash is carried from one call of intake to the next. A client that gets the 503 sends nothing again: it asks HEAD or the status route.

*One hand-over at a time.* The last request, the retry and the sweep all hand an upload over through one place, which keeps a table of the hand-overs in flight in this process: a caller that arrives while one runs waits for it and gets its answer, so an upload is hashed and recorded by one of them and the others read the result. A last chunk sent again is refused before it gets there, because an upload that is `finalising` takes no bytes.

*What a client sees.* The states of an upload, in one table for a client. Every HEAD of an upload carries `Urlog-Upload-State` with the state the status route (`GET .../uploads/{id}`) reports.

| State | What answers | What a UI shows and does |
| --- | --- | --- |
| `receiving` | PATCH 204 with the new `Upload-Offset`; HEAD 200 with the offset | a progress bar from offset and length. After a cut it asks HEAD and goes on from the offset |
| `finalising`, last request in flight | HEAD **423** with the header; `Upload-Offset` equals `Upload-Length` | "verifying": every byte is stored and the file is being hashed and recorded. It polls the status route and sends nothing |
| `finalising`, last request ended **503** | the last PATCH answered 503 with `Retry-After` and the problem type `upload-pending`; HEAD 200 | "verifying" as above. The record waits for the metadata file and the server tries again by itself. The client never sends the chunk again |
| `done` | status route: the file id, the SHA-256, the job | the file in the list of the case, with its parse |
| `duplicate` | status route: the id of the record that already holds the bytes | "already in this case", with a link to that file |
| `rejected` | status route: the reason (a packet capture) | the reason. Nothing was stored |
| `failed` | status route: the reason | the reason. The upload can be started again |

Refusals at creation: 400 with the metadata key named, 409 when the case is not active, 413 over the size limit, 507 when the queue is paused or the volume would fall under its mark. Refusals of a chunk: 409 when the case was closed meanwhile, 460 when the checksum does not match, in which case the chunk is cut back to where it began.

*Expiry.* An unfinished upload expires 24 hours after its last byte (`Urlog:Upload:Expiry`). A sweep, at start once the store identity comparison has passed and every 15 minutes after, removes expired uploads with their sidecars. It opens no path outside `<case id>/.uploads` and leaves alone a file there that does not carry one of the server's upload ids. An abandoned upload leaves no audit row: nothing of it became evidence.

*Never served.* The evidence root is reached through the API and its case ACL only. No route returns the content of an upload or of an evidence file, the static file handler serves the web root alone, and the host refuses to start when the evidence root lies inside the web root.

*In front of the backend.* A reverse proxy must stream request bodies on the upload route (nginx `proxy_request_buffering off`), set no body size limit there (`client_max_body_size 0`), and allow the last chunk's request the time intake needs to hash the file (a read timeout of ten minutes covers 20 GB many times over). PATCH, HEAD, DELETE and OPTIONS pass, with the `Tus-Resumable`, `Upload-*` and `X-CSRF-Token` request headers and the `Location`, `Upload-Offset`, `Upload-Expires` and `Tus-*` response headers. `Location` is a path, so nothing needs rewriting.

*Measured* (dev box, Release, the backend as its own process with the job runner off, sender and evidence root on one disk, `tools/upload-measure.ps1`). One upload of 21,474,836,480 bytes, the limit exactly, in 16 MiB chunks with a SHA-256 checksum each; the connection was cut inside a chunk near 7 and near 15 GB, and both times the upload went on from the start of the cut chunk, free again 0.3 s after the cut. 201.9 s in all: 157.8 s while bytes arrived (about 130 MiB/s) and 44.1 s for the last chunk's request, which is the hash and the record. The backend's working set, read once a second, was 178 MiB before the first byte and between 206 and 218 MiB from then to the end, the 44 s of hashing included. The SHA-256 computed by the sender, the one in the record and the one of the stored file read back from disk were equal.

**SFTP drop.** `/var/lib/urlog/intake/<case-id>/` served by the OS sshd/sftp subsystem with a per-case Unix group; the tool writes no SFTP server. Watcher uses inotify `close_write` + `moved_to`, then requires the file size stable for 10 s before enqueueing. Documented convention: upload as `.part`, rename on completion. Periodic rescan every 60 s catches missed events (inotify overflow, NFS). On startup the watcher reconciles directory contents against the database. A file dropped for a case that is no longer active is not taken in: the watcher moves it to `<case-id>/late/` and writes an audit row. The folder name is reserved (`CaseFolders.Late`); the move arrives with the watcher, and until then nothing reads a drop directory at all.

**Integrity, both paths.**

1. SHA-256 streamed over raw bytes before any decompression, normalisation or parsing: the content is hashed before anything reads or parses it. A rename on the same volume reads nothing and may come first, which is how a finished upload gets its final name before it is hashed there.
2. File owned by the service user, mode 0440, under the per-case directory. No `chattr +i`: it needs a capability the service should not have and breaks purge on overlay and NFS.
3. Idempotent on hash within a case: same bytes -> one record, logged as duplicate, not re-parsed. The `file_duplicate` row says where the second arrival came from (its name, its archive path, the host it was given or inferred), and the surviving record lists every other place its bytes were seen (`files.seen_paths`). Two members of one archive with the same bytes, the same file under two host folders for instance, are one record under the first host, and they are parsed once. The same bytes under two host folders are far more often one log collected twice (a shared mount, a collector's copy, a rotation picked up again) than two machines that wrote identical files, and a parse per host would count every event of it twice in every figure of the case. A format that names its host in the event is not affected: its rows carry the host each line states. The second place is not lost: the file's record lists every path and host its bytes were seen under, the files route shows it (`seen`, and the flag `seen_elsewhere`), and a person who decides the file belongs to the other host moves it there with one call, which parses it again.
4. Hash re-verified on every parse, in the same read: the job runner hashes the raw bytes as the pipeline reads them and compares the digest and the byte count with the intake record after the last byte, before anything is committed. The file's rows are invisible until that commit (the view above), so a file that fails the comparison was parsed and never shown: its rows are deleted, the job is `failed`, the file is `quarantined` and never queued again, and `integrity_mismatch` is written in the same transaction. A periodic integrity sweep re-hashes everything and writes results to the audit log.
5. Intake record: `{case, sha256, size, original name, source (web/sftp), uploader or OS user, received-at, host, source timezone, encoding, detector guess, override}`.
6. One transaction writes the record, its `file_intake` audit row and the job the file needs: a parse for a log, an expansion for a container, none for a file that is only kept. A file is never recorded as received with nothing queued to act on it.

**Compressed input.** gzip, zstd, xz and bzip2 are decoded in the parse pipeline by `CheckedDecodeStream` (`src/Core/Pipeline`), which wraps each decoder and reports how the stored bytes ended: complete, truncated, or damaged. The decoders cannot be asked. The runtime's gzip stream returns end of stream at any cut, the eight trailer bytes included, and the zstd, xz and bzip2 libraries report a short file, a damaged file and a file with extra bytes at its end in ways that cannot be told apart. So each format has its own check.

| Format | How the end is found | Truncated when |
| --- | --- | --- |
| gzip | when the stored bytes end, the decoder is fed one more gzip member, a sentinel whose content is a fixed 32-byte random constant; a decoder that had finished its last member hands out exactly that content | the sentinel's bytes are read as the rest of an open member: an error, other bytes, or nothing |
| zstd | the reader walks the frame structure (header length from the descriptor byte, each block's size and last-block flag, the optional checksum) and gives the decoder one frame at a time | the stored bytes end inside a walked frame |
| xz | a valid stream footer (CRC-32, backward size, flags, `YZ`) ends the stream | the stored bytes are at their end and the footer is missing |
| bzip2 | the end-of-stream marker with its 32 CRC bits is within the last 64 bytes the decoder took | the stored bytes are at their end and the marker is missing |

A truncated input reads as an ordinary end of stream, so everything before the cut is parsed, and the stream's `InputEnd` carries the decompressed offset and the stored offset of the end. Damage (a wrong checksum, a broken block in the middle of a whole file) stays an exception and fails the job. A cut exactly between two gzip members, two zstd frames or two concatenated streams leaves a valid shorter file, and no reader can tell it from a whole one. The first one to three bytes of a further member's magic with nothing behind them count as a truncation.

*Trailing bytes.* Stored bytes behind the last complete member, frame or stream that start no further one (NUL padding, or anything else) are neither content nor a truncation. The input is complete and `InputEnd.TrailingBytes` holds their count. Left to themselves the decoders disagree here: gzip stops without a word, xz stops without a word after its first stream, and zstd and bzip2 fail the whole file. For zstd, xz and bzip2 the reader knows where the last frame or stream ended, so the count is exact. The gzip decoder does not say where it stopped, so the last 80 KB of a gzip file are handed to it one byte at a time: it asks for the next byte only when it has used the one before, and the byte at which it stops asking is the first trailing one. A count reported as exact is proved. Two cases cannot be proved, and there `TrailingBytesExact` is false and the count is a lower bound: trailing bytes that reach back further than 80 KB are met inside a larger block (short by less than one block), and trailing bytes that begin with 0x1F behind a file of several members cannot be told from a last member whose length field ends in 0x1F (short by at most one byte; with one member the length field is checked against the decoded length and the count is exact). xz allows zero padding between streams; zeros are trailing only when no stream follows them.

The wrapper also guarantees four things the libraries by themselves do not:

- **Every stream of a concatenated xz or bzip2 file is read**, one library stream per stored stream. The xz library's stream reads the first stream and reports the end, and the rest of the file would be lost without an error.
- **bzip2 content never includes an unverified block.** The library decodes a block that is cut short as if the missing bits were ones, hands the result out, and only then finds the block CRC wrong. The wrapper releases bzip2 content one block late: the library reads stored bytes only while it loads a block, so a read that moved the stored position proves the block before it. At a cut the content ends at the last proved block, less at most 4 KB (one read that held the end of that block and the start of the next).
- **The content of a cut file does not depend on who reads it.** When the xz library meets the cut it throws, and what it had decoded in that call is lost with the exception; read with the pipeline's 64 MiB chunk buffer, that could be most of a file. The wrapper reads xz 16 KB at a time through a buffer of its own, so a cut xz file ends at most 16 KB before the cut, and the same stored bytes give the same content and the same offsets for every reader. gzip and zstd lose nothing at a cut; bzip2 ends at its last proved block.
- **The stored stream stays open until the job has hashed all of it.** The bzip2 library closes the stream under it when the data ends. The job runner reads the rest of the file through SHA-256 after the last decoded byte, so without the guard every bzip2 job ends with "Cannot access a closed Stream". Only the wrapper's own disposal closes the stored stream.

*What this depends on.* The gzip check rests on one behaviour of the .NET runtime that its documentation does not promise: `DeflateStream.Read` asks the stream under it for more input only when the current read has produced no output. That is why everything handed out before the sentinel is known to come from stored bytes, and why the byte-at-a-time window finds the first trailing byte. The bzip2 release rule rests on the library reading stored bytes only while it loads a block, and the xz and bzip2 stream ends on those libraries reading no further than the stream they decode. None of this is assumed silently: `CheckedDecodeStreamTests`, `GzipMemberCutTests` and `TrailingBytesTests` cut whole and built files of every format at every byte and fail if any of it changes. A bump of the .NET runtime, of ZstdSharp or of SharpCompress reruns those three classes before anything else (CONTRIBUTING.md, "Upgrades").

*Measured* (.NET 10.0.14, ZstdSharp 0.8.8, SharpCompress 0.50.8, dev box, quiet, Release). Decoding the 1 GiB nginx fixture from gzip (121 MB stored, 8.85:1) and discarding the output takes 609.7 ms through the runtime's stream alone and 627.6 ms through the checked reader, 1,761 against 1,711 MB/s of decoded bytes: the check costs 2.9 %, nearly all of it the 80 KB fed singly (`DecodeGzip`, reported, not gated).

**Intake pipeline** (`IntakePipeline` in `src/Core/Intake`). Every delivery path calls it once the bytes are on disk. It hashes the file (step 1), makes it read-only when it lies under the evidence root (step 2), detects it from the first 64 KB and the last 4 KB, derives the hints, and writes the record with its audit row and its job (step 6). It decodes nothing: decompression, expansion and parsing are jobs, so the one-job-per-case rule, the attempt cap, the watermark and the invisible-until-commit rule hold for archives without anything of their own. A packet capture is refused: nothing is recorded, and a `file_rejected` row on the case keeps its name, size and SHA-256. `IntakeGate` answers a caller that can still decline bytes (an upload that has not started): no for a case that is not active, no while the ingest queue is held by the disk watermark (the newest of `ingest_paused` and `ingest_resumed` in the audit chain), and no when the intake volume, less the bytes about to come, would be under the larger of 20 GB and 10 % of the volume. A file that is already on disk is never turned away; it is recorded and its job waits.

**Truncation on the record.** The commit of a parse takes the end of the input as a required value with no usable default: `JobOperations.CompleteAsync` refuses `InputEndKind.Unknown` before it opens its transaction, and no other code sets a file to `parsed` (a test scans the source for it). A truncated input is committed with `files.input_truncated`, the decompressed offset and the stored offset of the end, and an `input_truncated` audit row, all in the commit's transaction, so its rows become visible only together with the statement that the input was cut short. Trailing bytes are a note on the record (`trailing_bytes`, with `trailing_bytes_inexact` for a lower bound). The same commit writes the file's least and greatest event time (`ts_min`, `ts_max`), taken from each batch's timestamp column as the batch is handed to the sink, outside the parse pipeline. `urlog ingest` has no file record to flag, so it does not commit a truncated input unless `--allow-truncated` is given.

**Archives.** A zip, a tar, a compressed tar or a second compression layer is a container. Its `expand` job (`ArchiveExpander`, `src/Core/Intake/Archives`) turns it into one record per member:

1. The container is read once through SHA-256 and compared with its own record, as a parse does; a mismatch quarantines it and records no member.
2. Every entry is listed. Each regular file is read once through SHA-256 and detected like a file that arrived by itself. Directories, links and devices are listed and never opened or followed. Nothing is written to the metadata store in this pass.
3. The members are recorded in transactions of 200, each with its audit rows, its jobs and the container's resume point (`files.expanded_members`). An expansion that stops goes on behind the last whole batch and writes no row twice.

A member is a row of `files` like any other, unique on `(case, sha256)`, with `parent_file_id` (the nearest container), `root_file_id` (the file that arrived), `archive_depth`, `member_ordinal`, for tar `member_offset`, and `archive_path`, the whole chain: `bundle.zip!logs/inner.tar.gz!web-01/nginx/access.log.3`. Its SHA-256 and size are over its bytes as the archive holds them, so a `.gz` member is hashed compressed. A member that is a log gets a parse job; a member that is a container gets a record and an expansion of its own; anything else is recorded and kept; a packet capture is refused with its audit row. An entry name is data only. No member is written to disk under a name from an archive, so a name like `../../etc/passwd` is a string in a column.

A zip entry whose content cannot be delivered is still a member. The runtime's zip reader is no help in telling: it does not check an entry's CRC-32, and it hands out the bytes of an entry marked encrypted as if they were its content (measured on .NET 10.0.14). The expansion checks both itself, the CRC-32 over the content as it is hashed. An entry that is encrypted, uses a compression method the runtime lacks, or does not match its CRC-32 gets a record in state `unreadable` with its archive path, the reason (`unreadable_reason`), the content size the zip states (`stated_size`) and a SHA-256 over its bytes as the zip stores them, marked as such (`hash_of_stored_bytes`; the `file_intake` row says `hash_of: stored_bytes`). It is never parsed and never queued, and the job's summary counts it.

Member bytes are read through the container, read-only, on every parse (`MemberStore`). A zip or tar that arrived by itself and uncompressed is read in place, and its members cost no disk. A container that cannot be seeked to a member as it is stored (a compressed tar, a container inside another) gets one seekable copy of its archive bytes under the cache directory (`Urlog:Intake:CacheRoot`, beside the evidence root by default), `<cache>/<case>/<file id>.body`. The copy is derived data and not evidence: it lies outside the intake directory, the integrity sweep does not hash it, it is written again when it is missing, and it goes when the case is archived or purged. Nothing rests on it being right, because every member read from it is hashed on every parse and compared with the member's own record, like any file.

The caps hold for a file that arrived and everything inside it (`ArchiveLimits`, `Urlog:Intake:Archive`):

| Cap | Default | When it is exceeded |
| --- | --- | --- |
| depth | 3 containers | the fourth is recorded with a message and not opened |
| expansion ratio | 200:1, decoded bytes over the stored size of the file that arrived, looked at once more than 64 MiB is decoded | the job fails |
| total decoded bytes | 250 GiB | the job fails |
| members | 100,000 | the job fails |

They are checked on the bytes that come out, never on sizes an archive states about itself. A job that fails at a cap says which cap and the measured value, and has recorded no member of that container, since the caps are met in the pass that writes nothing. A single compressed log is held to the same ratio and size in its parse job. An administrator can queue one failed archive again with limits given by hand (`urlog expand --file <id> --max-...`); the limits ride on that job alone, and the request with every limit is a `file_expand_rerun` row written in the job's transaction. Free space is read every 256 MiB while a seekable copy is written; under the watermark the copy is removed and the job goes back to the queue, which the watermark then holds.

A container that is cut short is expanded as far as it lists. A compressed tar whose compression ends early (the checks above) and a tar that ends inside an entry both leave the members before the cut whole; the member the cut falls in is recorded from the bytes that are there with `container_cut` and `input_truncated`; and the container's own record carries `input_truncated` with an audit row. A zip that is cut short has lost its directory, which is at its end, and cannot be listed: its job fails and says so.

**Host inference.** A format that carries no host takes it from where the file sat. `HostInference` matches the archive path, or the name of a file that arrived alone, against a list of path templates (`Urlog:Intake:HostPatterns`), first match first: `{host}` captures, `*` stays inside one path segment, `**` crosses segments, `{a,b}` is alternation. They are templates and not regular expressions because they come from configuration and run on names an uploader chose. The built-in list looks for a host folder above a well-known log folder (`**/{host}/var/log/**`, `**/{host}/{nginx,apache2,httpd,iis,syslog,journal,audit}/**`, the IIS and Windows event log folders), for an archive named after its host (`{host}.zip!**`, `{host}-logs.*!**`) and for a file named after it (`{host}_access.log*`). `/` and the `!` behind an archive name are different separators, so a folder pattern never takes `bundle.zip` for a host with a domain. A capture must be host-shaped (RFC 1123 labels with a letter, or an IPv4 address) and not a common folder name. An inferred host is applied, so the rows carry it, and the record says so (`host_inferred`, `host_rule`) until a person confirms or changes it. A host given by a person always wins and holds for every member of an archive. No match leaves the file unassigned: flagged, never blocked, parsed all the same.

**Source timezone.** Collected at intake: per-host default, per-file override, defaulting to UTC with a visible "assumed" badge on the host, the file and the TZ header. It populates `ParseContext.TimeZoneHint` and `YearHint` for formats with naive timestamps (RFC 3164 syslog, IIS, app logs). Formats carrying an offset ignore the hint. PCAP/PCAPNG is rejected with a clear message, not stored as raw. The zone becomes one offset per file, taken at the file's own time (its modification time, else when it was received) and never from the clock, so the same bytes give the same rows whenever they are parsed. A file read by a source with naive timestamps whose events lie on both sides of a change of its zone's offset is flagged `spans_dst`: its times may be one hour off on one side. The year for formats without one is the given year, else the year of the file's own time, one less when the first line's month is later than that month, else the year the file was received, marked assumed. The record keeps whether a person gave the year (`year_given`): a year given for an archive holds for every member, as the zone does, while a derived year does not, and each member derives its own from its entry's time. An unknown zone is refused at intake, and the ids are IANA ids on Linux and on Windows alike (Query language, `timechart` buckets, says how an id is resolved).

## Format detection

A dropped file is classified without the analyst picking a type, and nothing is lost: text no source claims goes to the `generic` source, and a file that is not a log is kept as an artifact. The detector (`FormatDetector` in `src/Core/Detection`) is a pure function of the first 64 KB, the last 4 KB, the file name and the size. `DetectionSample` does the I/O around it, read-only and after the SHA-256 exists: it reads the two samples and, when the file is one compressed stream, decodes the first 64 KB of its content. The function itself never decompresses, because a bzip2 block does not fit a 64 KB compressed head.

Every file ends as one of five kinds.

| Kind | Meaning | What intake does |
| --- | --- | --- |
| `log` | parsed by the named source, `generic` at the fallback | records it, queues the parse |
| `container` | zip, tar, or a second compression layer | records it and queues its expansion: every member gets its own record, hash and detection, with the archive path kept for host inference |
| `artifact` | not a log: a document, an image, an executable, a database, a key, an archive that is not expanded, an empty file, unknown binary | hashes and records it with the reason; parses it only when a person names a source for it |
| `unparsed` | a log format this build recognises and has no parser for: the binary systemd journal, `.evtx` until its source exists | records it like an artifact, with a message; detected again when the source list changes |
| `rejected` | PCAP and PCAPNG | refuses it with a message, stores nothing |

**Rules, in order.** The first that applies decides.

1. **Empty.** No bytes, or a compressed stream that holds none: artifact `empty`. It is listed like any other file, since an empty log is a finding.
2. **Packet capture.** PCAP in either byte order and resolution, PCAPNG by its block type plus its byte-order magic (the block type alone is `\n\r\r\n`, which text can start with): rejected.
3. **Compression.** gzip `1F 8B`, zstd, xz, bzip2: the layer goes into the container chain and detection continues on the decoded content. The parse pipeline removes one layer, so a second layer under the first makes the file a container. A stream that fails before any byte is decoded is artifact `damaged-<kind>`; one that fails later is flagged `decode_error` and detected from what was decoded.
4. **Archive.** zip (`PK`) and tar (`ustar` at offset 257) are containers. A zip whose first entry is `[Content_Types].xml`, `mimetype` or `META-INF/`, or whose extension is an office or Java package one, is an artifact. The member list is not part of the result: a zip's directory is at the end of the file and a tar's is spread through it, so intake lists members when it reads the archive.
5. **Known binary logs.** `ElfFile\0` is the EVTX source when one is registered, else `unparsed`. `LPKSHHRH` is the binary journal, `unparsed` with the `journalctl -o export` command in its message.
6. **Artifact signatures.** The list is `MagicTable`: PDF, OLE2, RTF, PostScript, the common image and media headers, PE, ELF, Mach-O and Java class, dex, wasm, LNK, SQLite, ESE, registry hive, minidump, prefetch, PEM, KeePass, JKS, disk and memory image headers, and the archives that are not expanded (rar, 7z, cab, ar, rpm, xar), which carry the message "extract and upload the contents". A signature that is plain ASCII and belongs to a binary format (`MZ`, `regf`, `OggS`) counts only when a control byte follows within the first 64 bytes, so a text line that starts with those letters stays text. A two-byte signature (BMP, DER, TrueType, ICO) counts only together with its extension. `<?xml` is not on the list, because Event Viewer exports start with it.
7. **Encoding.** A BOM; without one, UTF-16 when at least 90 % of one half of the byte pairs in the first 4 KB is NUL and under 10 % of the other half; otherwise UTF-8 with lossy replacement. The encoding is recorded on the file row, and the sample is transcoded to the UTF-8 the parse pipeline will produce before any source sees it.
8. **Text that is a script or a page by its first line.** `#!`, `<?php`, `<!DOCTYPE html`, `<html`: artifact.
9. **Scores.** Every registered source except `generic` scores the sample from 0 to 1 (`Sniff`, or `ISniffDetail.SniffDetailed` for a source with layouts): about 200 lines of the head and 50 of the tail. Every score is kept.
10. **Decision.**
    - Top score 0.8 or more: a log, parsed by that source, whatever the file is called. An artifact extension is recorded as the flag `extension_mismatch` with a message naming both. A second source at 0.8 or more makes the winner `probable`; ties go to the source registered first.
    - Top score below 0.8 and an artifact extension (`ArtifactExtensions`: documents, images, executables, scripts and markup, databases, keys, media, disk and memory images, fonts, configuration): artifact. The extension is read after compression and rotation suffixes are removed, so `access.log.3.gz` is `log`. Extensions that log exports use (`log txt out err json jsonl ndjson csv tsv xml evtx journal`) are never on the list.
    - Top score from 0.5 up to 0.8: a `probable` log, flagged in the UI.
    - Top score below 0.5: the content decides, and **control bytes alone never make a text file "not a log"**. A control byte is NUL, a C0 control other than tab, LF, FF, CR and ESC, or DEL. A window of the file is judged like this: runs of 16 or more NUL bytes are padding (what a crash or a power loss leaves) and are taken out; a window without any control byte is text whatever its lines; a window with some is text when, in what is left, they are at most 3 % of the bytes and a line break comes at least every 4 KiB on average (a window under 256 bytes needs none); a window that is padding alone, or leaves under 256 bytes, says nothing. The file goes to `generic`, band `fallback`, when its first 64 KiB reads as text, or its last 4 KiB does, or, looked at only when neither does, any further window does: 64 KiB at a quarter, a half and three quarters of the file and its last 64 KiB, or, for content that is read forward only (a compressed stream, a member of an archive), 64 KiB at 256 KiB, 1 MiB, 4 MiB and 16 MiB of it. So junk before, after or inside a log does not hide the log. Only a file none of whose windows reads as text is artifact `unknown-binary`. The numbers were set against measured samples (2026-11-25): every text shape, a NUL in every line included, stayed under 1 %; compressed and random bytes measure 10 % to 15 % with line breaks as frequent as in text, so the share is what tells them apart; executables 10 % to 76 %; the nearest binary was a page of a database file at 4.15 %.
    - UTF-16 without a byte-order mark is recognised before any of this (step 7) and transcoded, so its NUL bytes are never counted. Behind junk it is not recognised: the head decides the encoding.
    - A log whose sampled windows hold any control byte carries the flag `binary_bytes` with the share in its message; the file's record says so (`files.detected_control_bytes`, flag `control_bytes` on the file and as a count on the dashboard).
    - **What this does not close.** Each of these tests is a threshold, and someone who controls a file's bytes can shape it to pass or to fail one: text packed with control bytes past 3 % is kept as "not a log", and a binary with one clean window of text is parsed as lines. The detector is therefore never the last word on a file. A file kept as "not a log" is counted on the dashboard by its state, listed with the reason (`files.detected_format`, `detection.format` on the file), and sent to the parser as text by one action of a read-write member (`PUT .../files/{id}/override` with the `generic` source, which the evidence page offers as "Parse as text"); the decision is audited and stands beside what the detector found.
    - Control bytes in a file some source scores 0.5 or more do not change its kind either. The file is a log with the flag `binary_bytes` and the share of such bytes in the sample is recorded: a log with a block of NULs in the middle, or NUL padding at the end, is a log and a finding.

Until a source in this table exists its files go to `generic`, and they are detected again when it is registered.

**The detection record.** One per file, never per host or case: the winning source, its score and band, every other source's score, the layout name where the source reports one, the encoding and whether a BOM named it, the container chain, the format of a non-log, what decided (signature, extension, content, scores), the flags and the message, plus the detector's rule version and the ids of the sources registered at the time. It is stored on the file row as `detected_kind`, `detected_source`, `detected_confidence`, `detected_layout` and whole as JSON in `detection`. A record whose source list or detector version is older than the current one is stale. `files.detection_registry` holds the detector version and the source ids a record was made with as one short text, so staleness is a comparison and no read of the JSON; a migration fills it for older rows from their records. A file is shown as stale (`detection.stale`, and counted on the dashboard) when a newer detector could send it to a parser: it has no override, it was taken for `unparsed`, went to `generic` or was kept as `unknown-binary` (which another rule may read as text), and its record was made by another detector version or source list. A person asks for such files to be detected again with `POST .../files/redetect` (`{"stale": true}`, or file ids). Detection reads evidence bytes, a member through its container, so it does not run inside the request: the route queues an ordinary job marked for it, and the job runner looks at the file with this build's detector before it parses. The new result replaces the record, and a `file_redetect` row keeps the kind, source, confidence, layout and detector of the record before beside those of the record after. A file that is now a log is parsed by its source in the same job. A file whose result is what it was, and a file that is still no log, end the job with that statement and no new generation, so the visible rows stay. An override is never touched by any of this. It is how a file that went to `generic` or `unparsed` reaches a parser added later. The layout is per file because the nginx source reports "layout unknown" at 0.6 when lines have its shape and no built-in layout fits, and two hosts behind one proxy can log two different custom layouts; a file with `nginx.log_format` in its options is scored against that layout only.

**Manual override.** Per file in the UI, re-parse on change. The override is stored beside the detection record and never replaces it, also when it names a parser for a file the detector took for an artifact: `detected_kind`, `detected_source`, `detected_confidence`, `detected_layout` and `detection` are not written by an override, and the files route shows the detection result, the override and what the next parse uses as three separate things. An override is a source id, options for the source, or both; an option a source does not know is refused, so a misspelt key is never stored and then ignored by every parse. A quarantined or unreadable file and an archive take none. An override that makes a log of a file the detector did not take for one cannot be cleared to nothing, since nothing would be left to parse it; it is replaced by another. Overrides can be bulk-applied to files with the same extension and detector result. What a person sees between the request and the new rows is under Cases, hosts, files and jobs API.

**`generic` fallback** (`src/Sources/Generic`). One event per non-blank line, `message` = `raw` = the line, full-text indexed, nothing rejected. A line longer than 1 MiB is written as 64 KiB events while more than 1 MiB of it remains and the rest as one; every such piece carries `extras['line.first_offset']` (the file offset of the line's first byte, the same on every piece) and `extras['line.part']` (`2/3`), takes the time of the first piece and is not searched for one of its own. When the chunk reader has to cut a record that outgrew its buffer, the line goes on in the next chunk and the same marks are written; its total is not known while its first pieces are written, and those say `2` instead of `2/3`. Pieces of files parsed before this carry no marks until the file is parsed again. The timestamp is the leftmost of four shapes within the first 256 bytes of the line: ISO 8601 with or without a zone (`-` or `/` in the date, `T` or a space, a `.` or `,` fraction), BSD syslog (`Mmm d HH:MM:SS`, year from the line or tracked from the hint), Common Log Format, and a Unix epoch of 10 digits (optionally with a fraction) or 13 digits, the epoch only at the start of the line or behind a `ts`, `time` or `timestamp` key and only between 2000 and 2100. Shapes without a zone take the source timezone. This is the one regex in the parsers: a source-generated alternation run over a stack copy of the window, so it still allocates nothing per row; a candidate that is no real date (month 13) is skipped and the search continues. A line without a timestamp takes the last one found before it in the file, so a stack trace sorts with the event that produced it; before the first one it takes the file's own time (`ParseContext.FileTime`, from `files.file_time`: the modification time where intake knows it), and with neither the column keeps its default. Those rows say which in `extras['timestamp.source']` (`previous`, `file`, `none`). Carrying a timestamp forward needs the file in order, so the source is `Stateful`. A line longer than 1 MiB is written as 64 KiB records while more than 1 MiB of it remains and the rest as one record. Files that went to `generic` can always be parsed again when a parser is added, because the original bytes are kept. The source is outside the throughput SLO: its bench entry is reported and listed as ungated.

**What the first real evidence set showed.** Recorded as shapes only. Uploads are not all logs: office documents, images, executables, database files and certificates sit next to them, which is why the artifact kind exists and why a fallback that turns every file into rows is wrong for them. Binary systemd journals arrive beside the text logs. Archives are nested (a tar inside a gzip inside a zip), and rar appears next to zip and tar. Windows events come in three forms: binary `.evtx`, Event Viewer XML exports in UTF-16, and EvtxECmd JSON and CSV. IIS W3C logs and SQL Server CSV exports (UTF-16, with `<c/>` standing for a newline inside a field) are common on Windows hosts. GitLab writes JSON lines with its own key set. Kubernetes nodes give CRI and Docker-JSON wrappers around application lines, klog, and ingress-nginx access logs. Rotated and compressed copies of plain logs are most of any upload. Two hosts behind one proxy used two different custom nginx layouts.

**Testing.** `fixtures/detection/<group>/` holds whole synthetic files in the shapes exports have, at least 20 per registered source (`nginx`, `syslog`, `generic`), plus `adversarial` (nginx with JSON user agents, syslog without PRI, a UTF-16 Event Viewer export, mixed formats, logs with artifact names and an artifact with a log name, NUL blocks inside a log, damaged and doubled compression, empty files, text that starts like a binary signature), `artifact` (a signature and padding per family), `journal`, `rejected` and `container`. Each group's `expected.tsv` says what the detector must report per file (kind, source, band, layout, encoding, chain, format, flags), and one theory in `tests/Sources.Tests` walks the directories, so a new source adds a directory and is covered. The files are written by `FixtureWriter` in the same test project, with a fixed seed and its own gzip, xz, zip and tar encoders (stored blocks, so the bytes do not depend on a compression library's version), and a test requires the committed files to be what it writes, byte for byte. The rules alone, with sources that return fixed scores, are in `tests/Core.Tests/Detection`.

**Measured** (dev box, quiet, Release). The detector on one sample with the nginx, syslog and generic sources registered (`DetectFormat`): 0.146 ms for an nginx or a syslog file, 0.120 ms for text no source claims, 0.107 ms for UTF-16 (448 KB allocated for the transcoded copy), 0.16 µs for a file decided by its signature, against a budget of 50 ms per file. The bench is reported and not gated (its syslog case measured 0.146 and 0.119 ms in two runs of the same code); the budget itself is a test over the fixture corpus. The detector theory over the fixture corpus (154 cases) runs in 1.3 s, and no file of it takes more than 50 ms (a test). The generic source on its 1 GiB fixture of mixed application-log lines (11.8 M lines, 31 % without a timestamp of their own, 0.8 % blank; `TokeniseGeneric`, one core): 754 MB/s and 8.2 M rows/s with 0 B per row, every non-blank line a row, no rejects, a timestamp found on exactly the lines that carry one. The number is recorded and not gated. `FileTime` in the parse context and the layout interface on the nginx source cost the gated tokenisers nothing measurable (`TokeniseNginx` 925.9 ms without and 936.1 ms with them, `TokeniseSyslog` 763.1 and 765.5 ms, both 0 B per row).

## Parser plugin contract

A source is one class; adding Dovecot means one class, one fixture pair, one benchmark fixture and one alias entry, with no core changes. Plugins never open a file, touch a socket, or allocate per event.

```csharp
interface ILogSource {
    SourceInfo  Info    { get; }  // id, aliases, display name, version
    Framing     Framing { get; }  // Line | MultiLine(startPattern) | BlankLineRecord | Binary(IChunkSplitter)
    FieldSchema Schema  { get; }  // declared columns + types; which map to ts/host/severity/message
    float Sniff(ReadOnlySpan<byte> head, ReadOnlySpan<byte> tail, SniffContext ctx);
    void  Parse(ReadOnlySequence<byte> framedChunk, ParseContext ctx, IBatchWriter batch);
}
```

| Responsibility | Owner |
| --- | --- |
| File I/O, decompression, encoding, archive expansion | core |
| 64 MB chunking split on record boundaries, framing per `Framing` | core |
| Columnar `IBatchWriter`, flush at 100k rows, Native serialisation, inserts, backpressure | core |
| Host/file/case assignment, metrics, error accounting | core |
| Tokenising a framed chunk into typed columns | plugin |
| Rejecting unparseable records via `ctx.Reject(span, reason)` → written as `raw` in the same batch | plugin reports, core writes |

`ParseContext` supplies `FileId`, `DefaultHost`, `TimeZoneHint`, `YearHint`, and a per-file scratch slot for state such as last-seen timestamp for monotonic repair. `FileTime` is the file's own time as intake recorded it, for the generic source only. A source with layouts also implements `ISniffDetail`, which returns the layout name next to the confidence and receives the file's options; the detector calls it in place of `Sniff`. Core guarantees a framed chunk never splits a record.

**Chunk pipeline** (`src/Core/Sources`, `src/Core/Pipeline`). `IBatchWriter` addresses the pinned columns by the `EventColumn` enum (`AppendUInt64/32/16`, `AppendTimestamp`, `AppendString`, `AppendIp`, `AppendExtra`, `CommitRow`); unset columns default, core stamps the identity columns and the default host, LowCardinality columns are ASCII-lowercased on the way in. `ctx.Reject(bytes, fileOffset, reason)` writes the record as a row with `raw` = `message` = the bytes and `extras['reject_reason']`. Plugins walk a chunk with `framedChunk.Records(Framing, ctx)`, a ref-struct enumerator that strips `\n`/`\r\n` and yields the decoded-stream offset of every record. The chunk reader cuts on the framing's last record boundary and carries the tail; a record longer than the chunk grows the buffer up to `max(ChunkBytes, MaxRecordBytes)` (64 MiB / 16 MiB by default), beyond which it is force-split and both chunks are flagged for the parser. Decompression (gzip, zstd, xz, bzip2) and UTF-16 transcoding wrap the input stream, so `file_offset` is always an offset into the decoded UTF-8 bytes. Chunk buffers and `EventBatch`es come from pools the pipeline owns (`PipelineBuffers`, sized by `PipelineOptions`: `InFlightChunks × ChunkBytes + (Parallelism + InFlightBatches) × BatchBytes`, about 1.4 GB at the defaults on 8 cores, about 190 MB with `PipelineOptions.SmallBox`); `ArrayPool<byte>.Shared` is not used because it trims under memory pressure. A `Stateful` source runs its chunks in order on one parser thread; everything else runs on `Parallelism` threads, unordered. The reader hands a chunk to the queue with `TryWrite` and waits with `WaitToWriteAsync` when it is full, so a chunk has one owner at every moment (a cancelled `WriteAsync` can throw after its item was queued, `tools/repro-channel-cancel`). A failed run reports the first failure in time: each task records its failure before it cancels the others, and a later failure is logged at debug level with its chunk context, not thrown. `EventBatch` is a struct of arrays with string columns as one byte buffer plus cumulative offsets: the ClickHouse Native block layout, which the Native writer serialises directly without row objects.

**nginx source** (`src/Sources/Nginx`, `src/Sources/Common`). The nginx/Apache source parses the combined and common formats by delimiter scanning (`IndexOf` for unquoted fields, a fixed-width timestamp check, one `SearchValues` of `"` and `\` for the quoted fields) at 1,273 MB/s on one core of the dev box with 0 B/row. `message` is the `"request" status bytes` slice of the line, not the whole line, so the text index does not carry the user agent and referrer twice; those live in `extras` (`user_agent.original`, `http.request.referrer`) and in `raw`. `event_code` carries the HTTP status next to `http_status` so 4xx and 5xx are integer filters; `event_outcome` is `success` below 400 and `failure` from 400. The extras key list and the catalog aliases are in `src/Query/field-catalog.yaml`. The `EventBatch` extras columns grow their offsets past `BatchRows`, since a source may write several pairs per event. `IpText` (IPv4/IPv6 text to bytes) and `Iso8601` are shared by the sources. **Layouts.** The nginx source is driven by a layout compiled from an nginx `log_format` string (`NginxLayout`): built-ins `combined`, `common` and `ingress-nginx` are detected per chunk, a custom format comes per file through `ParseContext.Options` (`nginx.log_format`, a format string or a built-in name; set at intake, later from the upload UI) and is then the only layout used. `NginxSource.Detect` reports the layout name with the confidence, or "nginx, layout unknown" at 0.6 when the lines have the shape but no built-in fits. Variables map to ECS keys where one exists (`request_time` → `event.duration` in nanoseconds, `upstream_*` → `upstream.*`), unknown variables keep their name in `extras`. The table-driven walk costs about 25 % over straight-line code, so the `combined` layout has an unrolled success-only scan that yields the same field positions (tests assert the agreement); every failure and every other layout runs the walk. `ParseContext.Options` is a generic per-file option bag for any source.

**Syslog source** (`src/Sources/Syslog`). The syslog source reads RFC 3164 (`Mmm dd HH:MM:SS host tag[pid]: msg`), the same shape with an ISO 8601 timestamp (rsyslog `RSYSLOG_FileFormat`), and RFC 5424 (`1 ts host app procid msgid sd [msg]`), each with an optional `<PRI>`, plus a Cisco-style `seq: ` prefix and clock marker; one `Tokenise` locates the header fields per line and serves `Sniff` and `Parse` alike (`Sniff` counts a line that starts with an ISO timestamp and has no PRI only in rsyslog's shape, a host-shaped token and then a tag, because most application logs start with an ISO timestamp too), at 1,390 MB/s and 10.1 M rows/s on one core of the dev box with 0 B/row. `host` is per event (the token after the timestamp unless it ends with a colon, the 5424 HOSTNAME field; otherwise the intake default), `program` is the tag (`postfix/<daemon>` becomes `program = postfix` plus `extras['postfix.daemon']`, the Postfix hook without Postfix field parsing), `severity` is the PRI's severity as rsyslog names it (`emerg` … `debug`), the facility name goes to `extras['log.syslog.facility.name']`, `[pid]` to `extras['process.pid']`, 5424 structured data to `extras['log.syslog.structured_data.<sd-id>.<param>']` with values as logged, and `message` is the text after the tag (a 5424 MSG BOM is dropped). 3164 timestamps are naive and take `TimeZoneHint` and `YearHint`; the ISO and 5424 timestamps carry their own offset. **The source is `Stateful`:** the year of naive timestamps is tracked across the whole file (Dec → Jan adds one, a late December line after January takes one back), which no per-chunk rule can get right for a multi-chunk file that crosses New Year, so core feeds a syslog file to one parser thread in order; at 1,390 MB/s that thread is not the ceiling (the insert path at 1 M rows/s is, on 120 B lines). Rejects: `empty line`, `bad timestamp` (nothing recognisable after the optional PRI), `truncated header` (5424 with fewer than six header fields), `bad structured data`; everything else is a row. Extras keys and aliases are in `src/Query/field-catalog.yaml`.

**Insert path** (`src/Core/Ingest`, `migrations/clickhouse`, ADR 0004). The insert data plane is our own native-protocol client: the driver exposes no raw connection and its column API needs one object per String, IP and Map row (a 248 B/row floor; the conversion measured 630 B/row and 340-1,470 ms per block), so `NativeBlockSerializer` writes an `EventBatch` straight into LZ4 frames (1 MiB payload each, CityHash128 checksums) over a socket speaking protocol revision 54449, with no per-row allocation. `NativeInserter` is the pipeline's `IBatchSink`: `Writers` (default 4) dedicated threads with one connection each, fed by a bounded queue (the backpressure); each writer keeps one INSERT open and streams batches into it until `MaxRowsPerInsert` (default 500k) or one second of silence, because the server squashes the packets of one INSERT into one part, so the pipeline's 100k batches still make 500k-row parts; a batch returns to its pool as soon as it is serialised, since a failed insert fails the job and the job's recovery is the delete of the attempt's rows plus a full re-parse. Measured on the dev box (ClickHouse in Docker Desktop, 8 cores shared): the `InsertNative` bench does 1.0-1.08 M rows/s with the text index on at 4 writers (flat to 6 writers and across 100k to 500k batches), 0.2 B/row, about one client core; the index costs 5-10 % of insert throughput (14 % of the server's CPU per insert); the dev box's burst ceiling at ~1.2 M rows/s is its Docker loopback (uncompressed blocks move at 0.3 M rows/s). Sustained over five minutes (330 M rows) the same path averages 0.7 M rows/s because ClickHouse spends 6 of its 8 cores on inserts plus the merges they cause; merges stay bounded (≤ 13 concurrent, ≤ 90 parts, drained in two minutes). Client-side sorting of unsorted (syslog) blocks was measured at −1 % to +4.5 % for twice the client CPU and is off (`SortBlocks`). The driver's TCP client stays for the control plane: `ClickHouseMigrator` applies `migrations/clickhouse/NNNN_*.sql` (embedded in the Core assembly) and records each file's SHA-256 in `schema_migrations`, refusing an edited file; `EventStoreAdmin` runs the lightweight deletes, the `file_generation` commit and partition drops. `events_v` filters `has(<parsed SQL_allowed_cases>, case_id)` through `getSettingOrDefault`, so no setting means no rows, and the committed generation of each file through a set built per query from `file_generation` (migration 0006: no row, nothing visible), read with the definer's rights, so no further account or grant is involved. `EXPLAIN indexes = 1` on a case+time query through the view prunes to the case's month partition and uses the primary key (integration test).

**Schema details and the query slice** (`src/Query`, `src/Cli`). The codecs of the schema above come from the per-column measurement (Scale section). The writer refuses a row that sets both `message_text` and a slice of `raw`, or a slice outside its raw. For the Map's LowCardinality keys the Native serialiser writes the key column with a per-block dictionary, its prefix before the array sizes, and nothing at all for an empty nested column, as the server does. The eight promoted columns that were extras keys: `http_method`, `http_version`, `http_response_body_bytes`, `http_referrer`, `user_agent`, `url_query` from nginx, `syslog_facility`, `process_pid` from syslog. `IBatchWriter.AppendMessage(offset, length)` is how a source sets the message. The query slice: `src/Query/field-catalog.yaml` (canonical names, types, the nginx and syslog vendor aliases, the known extras keys), a lexer and recursive-descent parser for the filter grammar plus `stats count [as x] [by f, …]`, `sort`, `head`, a transpiler to parameterised SQL over `events_v` with the case and time predicates first, every value a `{name:Type}` parameter, errors with positions and warnings (`unindexed`, `assumed_timezone`, `unknown_field`); 121 shared vectors in `src/Query/tests/vectors/` (61 of them error paths; any other verb is "not supported in v1: <verb>"). The query path runs over the driver's HTTP client as the read-only user with `SQL_allowed_cases` as a per-request setting and the parameters as `param_*` (ADR 0003); a case the setting does not list reads zero rows through the view. The CLI: `urlog ingest` (SHA-256 first, detection by every source's `Sniff`, the pipeline into the inserter, the `file_generation` commit, a generation above 1 deleting the file's rows first), `urlog query` (table, row count, elapsed, `--sql`, `--explain`), `urlog bench query` (p50/p95 over N runs, warm or with the server caches dropped).

**Discovery.** `[LogSource("dovecot", Aliases = ["dovecot-imap", "dovecot-lmtp"])]` on the class; a source-generated registry (AOT-safe, no runtime reflection scanning). Third-party plugins load from a `plugins/` directory with the same attribute.

**Testing contract.** Every registered source runs against `Fixtures/<source>/{sample.log, expected.jsonl}` for correctness and against a ≥50 MB benchmark fixture for throughput. A source below 50 MB/s/core fails CI unless marked `[Tier(Slow)]`, which excludes it from the SLO but still ships.

**Versioning.** `Schema` is versioned; a change bumps the plugin version and core migrates the ClickHouse table by adding a nullable column. Existing columns never change meaning.

**v1 sources.** syslog RFC 3164/5424, Postfix (sub-parser), journald export, Windows EVTX (Security, System, Sysmon; multi-Computer fan-out), nginx and Apache access + error, IIS W3C, JSON lines, CSV with header, `generic` (alias `raw`). Regex is permitted only in the `generic` fallback, which is outside the SLO.

## Throughput SLO and benchmark harness

**Target: ≥ 100 MB/s end-to-end** (file read → ClickHouse ack) on 8 cores, measured in uncompressed bytes, so 120 GB ingests in 20 minutes. Floor 50 MB/s (40 min). Below 25 MB/s is a failure.

| Stage | Budget |
| --- | --- |
| Tokenisers | ≥ 50 MB/s per core (≈ 250k nginx lines/s/core) |
| Insert path | ≥ 1 M rows/s via Native protocol |
| Writers | 4 parallel, \~250k rows each, \~1 insert/s per writer so merges keep up |
| Block size | a harness parameter, not a constant |
| Parallelism | chunked within a file (\~64 MB, newline-aligned), not per file: 2-4 systems × 1 week means a few huge files |
| Compressed input | decompressed inside the same chunk pipeline, counted against the budget |
| **Sustained, per format (dev box)** | burst 1.04-1.08 M rows/s in the gated `InsertNative` bench (SLO met, text index on); **sustained 0.7 M rows/s** over 5 minutes with ClickHouse at 6.2 of 8 cores on inserts plus merges → **~155 MB/s nginx (223 B/line), ~95 MB/s syslog (137 B/line)** |
| **Levers measured** | text index 23 %, merges 55 % of server CPU; the server config stays at its defaults (below) |

**Levers measured** (syslog, 120 M rows, dev box). Baseline 839k rows/s (114 MB/s). **1 M rows per INSERT: no effect** (`min_insert_block_size_bytes` splits a 381 B/row block at ~700k rows anyway). **The text index costs 23 % of sustained throughput** (a third of it at merge time: 39 % of part-write time, 31 % of merge CPU); accepted, the index stays synchronous. **Merges are 55 % of the server's CPU during ingest**; a 4-slot merge pool (`background_pool_size` 2, plus the three `number_of_free_entries_in_pool_*` thresholds below pool × ratio or the server refuses to start) gives 1,011k rows/s = 138 MB/s but 130 parts per 120 M rows and a 58 s drain, which reaches `parts_to_delay_insert` near a 120 GB case. **Recorded as the lever; the server config stays at its defaults.** The pool is never saturated (5-6 merges in 32 slots), so the knob is merges per insert, not threads.

The tokeniser budget applies to **text formats**. EVTX is binary XML with templates and substitutions, and the mature C# library (Eric Zimmerman's, MIT) is allocation-heavy; it is `[Tier(Slow)]`, outside the SLO, so the EVTX source ships without a change to the gate. EVTX volumes are a fraction of a bundle's bytes, which is why this is acceptable.

Row rate is driven by syslog (\~120 B/line → \~830k rows/s at 100 MB/s), which is why the insert budget is 1 M rows/s rather than the byte rate. Schema choices that keep per-row overhead low: `LowCardinality` on host/program/severity, `DateTime64(3)` with Delta codec, ZSTD(1) everywhere a String is (level 3 bought 2-4 % of disk for 3-7 % more CPU and was not taken), `message` as an alias so the record crosses the wire once, `async_insert` off.

**Harness.** BenchmarkDotNet micro-benchmarks per parser on fixed-seed 1 GB nginx and 1 GB syslog fixtures; one end-to-end benchmark against ClickHouse in Docker; raw disk read rate reported separately so a miss is attributable to hardware vs. code; insert path benchmarked alone. The gate is local-first: `bench/check-regression.ps1` compares against `bench/baseline.json` with a 10 % ceiling that cannot be raised, the pre-commit hook runs the touched source's `Tokenise*` benches (short job), and `tools/pre-merge.ps1` runs every `Tokenise*` and `Insert*` bench with the full job before a branch merges. The baseline changes only with `URLOG_BASELINE_UPDATE=1`. No parser merges without a bench entry. Speed never costs determinism: the same input produces the same rows.

Generic shippers (Vector \~66 MiB/s, Fluent Bit \~40, Logstash \~28) sit below this target, which is why the pipeline is not built on them.

## Query language

An SPL-flavoured pipeline, parsed to an AST and transpiled to parameterised ClickHouse SQL. ClickHouse does the optimising; the one optimisation the transpiler owns is pushing `case_id` and the time range to the partition and sort keys. Ambiguity returns a precise inline error, never a guess.

```
index=case-31 src_ip=10.0.0.5 EventID=4625 | stats count by user | sort -count | head 20
```

**Filter grammar**

| Form | Semantics |
| --- | --- |
| `field=value` | case-folded exact match on string fields; numeric compare on typed fields |
| `field=val*` | `LIKE 'val%'`, indexed |
| `field=*val*` | `ILIKE`, flagged unindexed in the UI |
| `!= < > <= >=`, `field IN (a, b)` | direct |
| `src_ip=10.0.0.0/8` | `isIPAddressInRange` on native IP types |
| bare term | token search on `message` through the `text` index, case-insensitive (ASCII lowering, as the index); `raw` is not searched for bare terms, because an OR with an unindexed column would defeat the index, and everything in `raw` but not in `message` is a typed column; a term of several tokens is each token through the index plus the exact text confirmed by `position` |
| `"quoted phrase"` | exact substring |
| `a b` / `OR` / `NOT` / `( )` | implicit AND, explicit OR and NOT, grouping |

**Time.** Relative (`-24h`, `-7d@d`, `now`), absolute ISO 8601, and inline `earliest=` / `latest=` overriding the picker. `@` snapping is computed in the display timezone. Default range is the whole case span (per-file min/max in the metadata DB), never "last 24 h". Always queried in UTC.

**The span of a case** is recorded with the case (`cases.ts_min`, `cases.ts_max`). The transaction that commits a parse recomputes it from the file records, so it follows a re-parse in both directions. Two kinds of event time do not count toward it (`EventTime` in `src/Core`). A time before 1980-01-01 UTC is no time: the column default of a rejected or undatable record is the epoch, and a timestamp without a year that was parsed with no year hint lands in 1970. A time more than one day after its file arrived is a wrong year guess or a wrong clock, since nothing is logged after it was collected; the day covers a collecting machine whose zone was taken for UTC. Rows outside the two bounds are stored and searchable like any other. They are counted per file and per case (`undated_rows`, `future_rows`), the case response and the field listing carry both counts beside the span, and a search reaches them with an explicit range. A file parsed before the counts existed has 0 in both until it is parsed again. `urlog query --db <file>` takes the recorded span and says how many events lie outside it; without a metadata file it takes the span of the case's visible events with the same floor, and has no arrival time for the second bound.

**Verbs: eight, no more in v1**

| Verb | Contract |
| --- | --- |
| bare search | the filter grammar above |
| `where <expr>` | the filter grammar. Before an aggregation it narrows the events (`WHERE`). After `stats` it compares the columns of the result (`HAVING`): aggregates by their name, by fields by theirs; a bare term is refused there, since there is no event left to search |
| `stats agg [as name], ... [by f1, f2]` | `count`, `dc(f)`, `sum(f)`, `avg(f)`, `min(f)`, `max(f)`, `values(f)`, `earliest(f)`, `latest(f)` (the value of `f` on the earliest and the latest event that has one; `earliest(_time)` is the first instant). Aggregates are separated by commas or spaces. `sum`, `avg`, `min` and `max` take an integer field, a time (`min`, `max`) or an extras key or rex group read as a number where it is one. A later verb names an aggregate by its `as` name, a bare `count` by `count`; an aggregate without a name is a column of the result that nothing can refer to |
| `sort [-]f` | `ORDER BY` |
| `head N` | `LIMIT` |
| `table f1 f2` | the columns of the result, in that order: fields for events, result columns after `stats`. A column `table` leaves out can still be compared and sorted on |
| `rex field=f "(?<user>\w+) from (?<ip>\S+)"` | each named group is a column for the rest of the query, never stored; `extractGroups`. `field=` is required and names a text field. The pattern is checked before any SQL exists (below) |
| `timechart span=5m agg [by f]` | one aggregate over time buckets, `span=` before the aggregate or after the by clause, units `s m h d w`. With `by`, the ten series with the largest aggregate over the whole range keep their rows and the rest are one series (below) |

No `eval`, `join`, `transaction`, `lookup`, `append`: v1 has nothing that does their work. Any other verb is refused with "not supported in v1: <verb>", and where v1 has another way to the same result the message carries it: `top` and `rare` (`stats count by f | sort -count | head`), `fields` (`table`), `dedup` (`stats count by f`, or `stats latest(raw) by f`), `rename` (`as`), `search` (`where`), `regex` (`rex` and `where name=*`), `chart` (`stats ... by`), `bin` and `bucket` (`timechart span=`), `tail` and `reverse` (`sort`). `count(f)` is refused with `f=* | stats count`. A raw-SQL advanced tab exists as an escape hatch under the controls in the Security section.

**Order of the verbs.** `search, (rex | where)*, [stats | timechart], where*, [table], [sort], [head]`. One aggregation per query. `where`, `table` and `sort` may trade places where the result is the same (`where` after `sort`, `table` after `head`). Refused, with both verbs named: a second `stats`; `stats` with `timechart`; `rex` after `stats`, `table` or `head`; `stats` or `timechart` after `table`, `sort` or `head`; `where` or `sort` after `head`; anything after `timechart`. A `where` sees the groups of the `rex` before it, and a group that an earlier `where` already read as a field is refused.

**A row without a value.** The columns are not nullable, so "this event has no such field" is a stored value: the empty string for a keyword, a string, text and an extras key; `::` for an address; and 0 for an integer column the catalog marks `zero_is_absent` (`event.code`, `http.response.status_code`, `process.pid`). An integer column without the mark always has a value, 0 included: a response of 0 bytes is a fact. **The limit this leaves:** a source that does not supply such a field stores 0 too (a syslog line has `http.response.body.bytes` 0), and the two cannot be told apart; narrow the search to the source when it matters. Three rules follow, the same as in Splunk. `f=*` is true for a row that has a value in `f`, for every type, and `f!=*` for one that has none. A row without a value in a by field is in no group of `stats` and no series of `timechart` (with several by fields, one empty field is enough). An aggregate over a field reads only the rows that have it, so `avg(status)` is not pulled down by lines that are not HTTP. A rex group that did not match is an empty string and falls under the same rules with no case of its own.

**`values(f)`** shows at most 100 values a group, in ascending order: numbers by size, times and addresses by value, text by its bytes, so upper case comes before lower case. A group with more shows its 100 smallest. The SQL asks for 101 (`groupArraySortedDistinct(101)(f)`): the reader of the result cuts a cell that holds 101 back to 100 and marks its row, and the result carries the `values_capped` warning only when some group did reach the cap. For the cell to be the same on every run the server holds every distinct value of a group while it reads; a cap inside the aggregate would hold 101 and return whichever it met first. Measured on 26.8.36.3 over 25 M generated rows in 10 groups, three runs each: with 50 distinct values a group the two forms are equal (about 100 ms, under 1 MiB); with 2 M distinct values a group, 20 M in all, the sorted form takes 1.6 to 1.8 s and 2.46 GiB against 0.09 s and 1.1 MiB, about 123 bytes a distinct value of 12 to 20 characters. The query profile's 4 GB bounds it: `values` of a field with tens of millions of distinct values over the groups of one query ends at the server's memory limit (code 241). That one refusal is explained to the analyst in place of the server's text: the query error says that `values(f)` passed the memory limit of a query because it keeps every distinct value of a group, and to count the values with `dc(f)` or narrow the search or the time range. A query without `values` that meets the limit keeps the server's code and first line. `tests/Security/SearchApiTests` runs both as an account whose limit no aggregation fits in.

**`earliest(f)` and `latest(f)`** compare rows by `(ts, file_id, file_offset)`, the key of a listing, so among several rows on the first or the last instant the same one is chosen on every run: the one a listing in that order shows first (`argMin` and `argMax` over the tuple). The key costs time and no memory: over the same 25 M generated rows `argMin` took 0.42 to 0.50 s against 0.13 s by `ts` alone and `argMax` 0.69 to 0.77 s against 0.14 s.

**`rex` patterns** are checked by `Re2Syntax` before any SQL exists, against the RE2 syntax the server compiles: literals, classes and POSIX classes, the escapes `\d \w \s \b \A \z` and their negations, `\pL`, `\x41`, `\Q...\E`, groups `(...)`, `(?:...)`, `(?<name>...)`, `(?P<name>...)`, the flags `i m s U`, alternation, and `* + ? {n} {n,} {n,m}` greedy or lazy. Lookahead, lookbehind, backreferences, atomic groups, possessive quantifiers, conditionals, comments and anything the checker does not know are refused with the offset of the construct in the query. Inside the quotes of the query only `\"` and `\\` are escapes, so `\d` is written as it is and a literal backslash in the pattern is four. Limits: 1,000 bytes; 16 capture groups (an unnamed group counts and is not a column), at least one named; a group name is letters, digits and `_`, unique in the query and not a catalog name or alias; a counted repetition is at most 100 and never inside another (RE2 itself stops at 1,000, measured); groups nest at most 10 deep; 4 `rex` a query. The pattern is one bound parameter. A pattern the checker lets through and the server cannot compile is a query error with the server's code (427). **Cost.** RE2 does not backtrack, so a match costs rows x bytes x program size, and the limits bound the program; the pattern runs only on the rows the case, the range and the search leave. What bounds the rest is the query profile (60 s and 4 GB a query), which a request cannot change, and `cancel_http_readonly_queries_on_client_close` on that profile, so a query whose client has gone is stopped (measured: gone from `system.processes` within 5 ms; without the setting it was still running 10 s later).

**`timechart` buckets.** Under a day the buckets are cut in UTC from the epoch (`toStartOfInterval(ts, toIntervalHour(n))`): a change of the clocks does nothing to them, the local labels skip or repeat an hour, and in a zone with a 30 or 45 minute offset an hourly bucket starts at :30 or :45 local time. A day or more is cut on the display zone's calendar and returned as a UTC instant. For an IANA zone the server does it (`toStartOfInterval(ts, toIntervalDay(n), zone)`); measured on 26.8.36.3: in Europe/Bucharest the bucket of 2026-03-29 is 23 hours long and that of 2026-10-25 is 25, both starting at local midnight, and in America/Santiago, where midnight of 2026-09-06 does not exist, the day starts at 01:00 local. For a fixed offset (`+02:00`), which the server cannot load as a zone, the instant is shifted, cut in UTC and shifted back, and every day is 24 hours. Weeks start on Monday; a span of several days counts from 1970-01-01 in that zone. A zone that is neither is refused for a span of a day or more. The display zone is resolved before the transpiler runs (`TimeZones.Find`), and an unknown id is refused there. The build uses invariant globalization, so the backend needs no ICU library, and a zone id is an IANA id on every system (`ZoneIds` in `src/Core`). On Linux, the deployment target, the id is read from the system's zone database. On Windows the system knows its own zone ids and the runtime would map an IANA id to one through ICU, which the build leaves out (measured on the development box: `Europe/Bucharest` is refused by the runtime as built and resolves once the setting is off). An id the system does not know is therefore looked up in the table of IANA and Windows ids that NodaTime carries: the Unicode CLDR mapping compiled into its assembly, managed code under Apache-2.0, in the version the ClickHouse driver already brings. The Windows zone the table names is returned under the IANA id, so the zone name a query sends to the event store is an IANA name. The same table knows the older names of zones (`Asia/Calcutta`, `Europe/Kiev`), which a Linux zone database may have dropped (Ubuntu 24.04 ships them in a package of their own): such a name resolves, on both systems, to the zone under the name it has today. Offsets and rules are the system's in both cases; NodaTime does no zone arithmetic here. The same resolver serves the source timezone of a host or a file, the upload hints and the CLI's `--tz`. An id that neither the system nor the table knows is refused with the same message on both systems. Two things follow from taking the rules from the system: a Windows backend applies the rules of the Windows zone an id maps to, which for dates far in the past are coarser than the IANA database's, and several IANA ids share one Windows zone; Linux is where evidence is parsed for the record. A zone object whose id has the IANA form but which the runtime cannot vouch for is passed to the server by name, and the server refuses a name it does not know (a query error). A span that would cut the range into more than 5,000 buckets is refused with the count. **Series.** The SQL returns one row per bucket and series (bucket, in-top flag, series, value), because a column per series would make data into column names; the reader pivots (`TimechartPivot`). The ten series with the largest aggregate over the whole range are found first (a CTE), ties to the smaller key; every other series is one row per bucket with flag 0, whose value is the aggregate over those rows, not a sum of series, so `dc` and `avg` stay right. `values`, `earliest` and `latest` are not numbers and are refused.

**Measured** on 25.2 M rows (the two 1 GiB fixtures twice as one case, 1.35 GiB, 56 parts in 16 partitions, half of the rows in 1970 and 11.6 M in March to June 2026), 20 warm runs each through `urlog bench query`, client wall time over HTTP on the development box:

| Query | Rows out | p50 | p95 | max |
| --- | --- | --- | --- | --- |
| `src_ip=X \| stats count by url.path` | 3,974 | 198 ms | 215 ms | 237 ms |
| `stats dc(source.ip) by url.path` | 3,974 | 641 ms | 691 ms | 732 ms |
| `timechart span=1h count by host` over March to June 2026 (11.6 M rows, 2,928 buckets) | 29,830 | 297 ms | 444 ms | 559 ms |
| `rex` with two groups, `stats count by` one of them, `sort`, `head 20`, over 1,001,444 rows | 20 | 138 ms | 156 ms | 319 ms |

The marks are 500 ms at p95 for the first and the third and 2 s for the last. **`dc` is exact and its figure is the measured one, 691 ms:** the cost is `uniqExact` itself (21,968 addresses over 3,974 paths), and the rule for rows without a value adds nothing. Server-side, best of five on the same table: as transpiled (`uniqExactIf`, the by field tested for a value) 0.626 s; `uniqExact` with neither test 0.662 s; `uniqExactIf` alone 0.655 s; `uniqExact` with the by field tested 0.611 s; the approximate `uniqIf` with both tests 0.467 s; `count()` by the same field 0.230 to 0.263 s. The timechart was taken over March to June because one-hour buckets over the whole table (1970 to 2026) are 494,000, far over the 5,000 a query may ask for. `EXPLAIN indexes = 1` on the timechart (both of its reads) and on `stats dc(user.name) by host` over March reads the 11 parts of that case's March partition out of 56 (Min-Max 11/56, Partition 11/11, 901 of 3,144 granules): the same pruning as a plain search. Two more properties of `rex`, measured: a pattern with several groups is matched once per row however many groups are read (one call 0.111 s, two calls written out 0.110 s, no pattern 0.066 s, over 1.17 M rows), and in an event listing the pattern runs only on the rows `LIMIT` keeps (`head 100` over the whole case: p50 1,379 ms without `rex`, 1,380 ms with it).

**Nothing the analyst writes is part of the SQL text.** A value is a bound parameter, and so is the key of a field the catalog does not list. A name the analyst invents (the alias after `as`, a `rex` group) must be an ASCII letter or `_` followed by ASCII letters, digits and `_`, 64 characters at most, and even then it is not written into the SQL: every output column that is not a catalog field carries a generated alias (`c0`, `c1`, ...), and the names the analyst sees travel beside the SQL as the result's column list (`TranspileResult.Columns`), which the query client puts on the result. The only identifiers in backquotes are catalog field names, which the catalog loader holds to letters, digits, `_` and `.`, and generated aliases. `tests/Query.Tests/SqlTextInvariantTests` asserts it over every vector and over 4,000 seeded inputs built from the characters that end an identifier or start a comment: the SQL uses only the transpiler's own characters, every backquoted identifier is a catalog name or a generated alias, and the SQL text is the same when each name and value is replaced by another of the same shape. The reason is a defect this replaced: a by field ending in a backslash escaped its closing backquote and the alias after it ran as SQL, without the query's case and time predicates, inside the caller's allowed cases. The view and the gate held (`tests/Security/IdentifierInjectionTests` sends that statement as it was). A query the gate lets through and the server then refuses is a `QueryFailedException` with the server's code, shown as a query error.

**Field catalog.** A YAML file of canonical ECS-subset fields: name, type, description, aliases (Splunk, ELK and vendor-native such as `Computer`, `IpAddress`, `remote_addr`). The query parser resolves aliases before transpiling; parsers write only canonical names. Contributors add aliases without code changes. Sigma rules already map to ECS, which is the v1.1 head start.

**Unknown fields.** A field name the catalog does not know transpiles to `extras['name']` (string compare, unindexed, flagged in the UI), so a JSON-lines key or vendor field nobody mapped is still reachable from SPL. Autocomplete offers `extras` keys seen in the per-case field statistics alongside catalog fields.

**Autocomplete** draws from three sources: the field catalog (fields, aliases, descriptions); per-case field statistics (which fields exist in this case and their most frequent values with counts, e.g. `EventID=` offers `4624 (12,041)`); and the verb list after `|`. All search state lives in the URL.

**Field statistics** (`FieldStatsTask` in `src/Core/Ingest`, the table `field_stats` in the event store). Per case: the number of events; for every keyword, int, ip and string column and every extras key, the number of events that have a value in it; for keyword, int and ip columns and the extras keys the catalog lists, the 100 most frequent values with their counts. **Top counts are exact**: each is a `GROUP BY` over the case's visible rows. **The number of distinct values of a field is an estimate** (`uniqCombined`) and is called `distinct_estimate` wherever it appears. It decides one thing: a field with more than 100,000 distinct values gets no top values, which bounds the hash table of its `GROUP BY`. A row without a value in a field is not counted for it, by the rule of the verbs above, so an empty string, `::` and a 0 the catalog marks absent are never top values. String columns (`user.name`, `url.path`, the user agent, the referrer, the query string) are counted and have no top values. An extras key the catalog does not list is reported with its count and without values, since nobody has said whether its values may be shown; a case reports at most 1,000 keys, most frequent first.

*What it reads.* The task runs as `urlog_ingest` and is, with the fill of the stored histogram, the only reader of `events` beside the view (Security, write path). Through `events_v` as the query account it would run under the analysts' 60 s limit and take slots from their searches. Every statement comes from `CaseScopedEventsQuery.BuildVisible`: the case first, then the committed-generation filter of `events_v`, the same text (a test compares it with migration 0006). The task therefore counts what an analyst's query counts, and never the rows of a parse that is not committed or that a re-parse has replaced (`tests/Security/FieldStatsTests`). The statements: one pass for the counts and the estimates, one `GROUP BY` per column within the bound, two reads of the extras map (the keys, then the top values of the listed ones).

*When it runs.* The commit of a parse marks the case in the same transaction (`case_stats.dirty_since`). A runner slot that finds no job to claim takes the case that has been marked longest, when the case is active or closed, has no job running and none it could still run, has no lifecycle work under way, and its last commit is at least 15 s old (`Urlog:Ingest:Stats:QuietPeriod`). Ten files of one case that are parsed in a row end in one run, after the last. A closed case with jobs held since its close is not kept waiting for them. One run at a time in the process; it holds its slot, so at the default of one slot nothing is parsed beside it and a new file waits at most the run's time limit (10 minutes by default; the run itself is about 11 s per 100 M rows, below). `urlog worker --once` does not wait for the quiet period. A case whose file records sum to more rows than `MaxCaseRows` is not read at all: an older set is removed and the case says why (`skipped`, with both numbers). A run that passes its time limit or fails writes nothing, leaves the older set in place and records `timed_out` or `failed` with the reason; the next commit marks the case again. A stop of the runner records nothing and the mark stays. A run clears the mark only if no parse was committed since it began. No audit row is written: the statistics are derived data. They go with the case's partitions at archive and purge, and after a re-import the commits of its parses mark the case, so the runner that closes it rebuilds them.

*Limits, and what they rest on* (`Urlog:Ingest:Stats`). Measured on the development box, quiet, in a scratch store, 2026-11-18: one case of 25,239,638 rows (the two 1 GiB fixtures twice, nginx and syslog, plain and gzip; 22 parts in 4 partitions, 1.41 GiB), 49 fields, `urlog bench stats`, five runs after the parses and their merges: 2,968 to 3,206 ms, median 3,104 ms, against a mark of 60 s. The set is 315 rows; its insert and delete take 14 to 96 ms of that. By statement, slowest first (first run): the pass over the columns 1,174 ms, top `source.ip` 319 ms, the top values of the extras keys 248 ms, the extras keys 223 ms, top `process.pid` 191 ms, every other `GROUP BY` under 110 ms. Three fields were over the bound of 100,000 distinct values and got no top values: `file.offset` (12.6 M), one structured-data key (371,114) and `http.response.body.bytes` (159,325). By threads, median of three runs: 8,966 ms at 1, 4,949 ms at 2, 3,104 ms at 4, 2,430 ms at 8. The largest memory one statement used was 67 MiB (top `process.pid`, 4 threads).

*The cost by size.* Same box, quiet, same day: one case grown in four steps from sixteen 1 GiB files (the two fixtures and seven pairs written by the same generators from other seeds, so the distinct values grow with the case), five runs at each size after the merges, 4 threads:

| Rows | Parts | On disk | Median run | Range | Per million rows | The pass over the columns |
| --- | --- | --- | --- | --- | --- | --- |
| 25,216,914 | 22 | 1.42 GiB | 2,787 ms | 2,735 to 2,944 | 0.111 s | 1,123 ms |
| 50,427,050 | 21 | 2.92 GiB | 6,301 ms | 6,072 to 6,812 | 0.125 s | 2,475 ms |
| 75,650,547 | 34 | 4.38 GiB | 7,942 ms | 7,929 to 8,000 | 0.105 s | 3,323 ms |
| 100,835,963 | 22 | 5.93 GiB | 10,726 ms | 10,706 to 10,817 | 0.106 s | 4,506 ms |

The cost is linear in the rows: four times the rows are 3.85 times the run, and the pass over the columns, the largest statement, is 4.01 times. The one step in the line is the bound on distinct values. `source.ip` had fewer than 100,000 addresses at 25 M and 50 M rows and its `GROUP BY` took 336 and 785 ms; from 75 M on it is over the bound, gets no top values and costs nothing, which is why the third row is cheaper per row than the second. A larger case therefore tends to run fewer statements, not more. Memory did not move: the largest statement used 69 MiB at every size. At 8 threads the 100.8 M-row run takes 9,431 ms (median of three), 1.14 times faster.

| Setting | Default | Reason |
| --- | --- | --- |
| `MaxThreads` | 4 | half of the reference box's cores for 1.28 times the 8-thread run; a search beside a run keeps the other half |
| `MaxMemoryBytes` | 1 GB a statement | 15 times the measured peak. The bound on distinct values is what keeps the hash tables small; the rest is room for values much longer than the fixtures' |
| `TimeLimit` | 600 s | 2.25 times the run of a case at the row limit, and the longest a file queued behind a run can wait for its slot |
| `MaxCaseRows` | 2.5 billion | a syslog case of 300 GB. At the measured 0.106 s per million rows a case of this size is a run of about 266 s; a 120 GB syslog case, about a billion rows, is about 107 s |

Three things these figures do not show. The row limit is 25 times the largest case measured: the line is straight from 25 M to 100 M rows and is assumed to stay so. The measured case (5.9 GiB) fits in the memory of the box, and a billion rows (about 60 GiB) do not, so a run there reads from disk; the time limit leaves a factor of 2.25 for that, and a run that passes it changes nothing and says `timed_out`. And the fixtures write few extras keys, because their common ones are columns, so the two reads of the map are cheap here; a source that writes many keys a row will make them the slowest statements, and is measured when it exists.

*What a run costs the queue.* Same day, a running `urlog worker`, five rounds: a one-line file queued for another case about 1.4 s after a run of 2.9 to 3.1 s had begun started its parse 1.10 to 1.29 s after it was queued, when the run ended. The same file queued with no run under way started after 0.47 to 0.59 s (an idle slot looks at the queue once a second). A file queued in the first instant of a run waits the whole run: about 3 s on this case, about 11 s on 100 M rows, by the same line about 107 s on a billion and 266 s at the row limit, and 601 s at the worst (the time limit and one look at the queue). A run starts only when the queue is empty and the case has been quiet for 15 s, so the wait falls on a file that arrives while a run is under way, not on files that arrive together.

*Replacing a set.* A run writes its rows in one INSERT, all with one `computed_at`, which is later than that of the set it replaces whatever the clock says. It then deletes the case's older rows. Readers go through `field_stats_v` (migration 0008), which shows for each case the rows of its newest `computed_at`, found in the same scan as the rows by a window over the case, so one snapshot of the table decides. A reader gets the whole old set or the whole new one, also between the insert and the delete (measured on 26.8.36.3: an insert of 120,000 rows is one part; `tests/Security/FieldStatsTests` reads during 30 swaps and in the state between the two statements). The table is a ReplacingMergeTree on (case, field, value); a merge that folds an old row into a new one changes nothing the view shows. The rows of a set: `('', '')` holds the number of events, `(field, '')` the events with a value and the estimate, `(field, value)` one top value with its exact count.

*Reading it.* `GET /api/v1/cases/{id}/fields`, for any member of the case: every catalog field with its type, description, aliases, `sensitive` mark and `zero_is_absent` (an integer field whose 0 stands for "no value"), its `events`, `distinct_estimate` and `top`; the extras keys the catalog does not list, with counts; the verbs; the span with its two counts; and `statistics` with a state (`ok`, `none`, `skipped`, `timed_out`, `failed`, or `unavailable` when the event store does not answer), the reason, and `pending` while a newer run is due. The catalog half is served whatever the state, so autocomplete works without the counts. The statistics are read as the query account for the route's case alone (Security, query path).

*Sensitive fields.* The catalog marks a field whose values can name a person or carry a credential (`sensitive: true`): `user.name`, `source.ip`, `destination.ip`, `network.forwarded_ip`, `source.address`, `ident`, `url.query`, `url.original`, `http.request.referrer`, `message`, `raw`. The mark is passed on for the interface to act on and changes nothing in a query. Top values are stored for the two address fields, `network.forwarded_ip`, `source.address` and `ident`. None are stored for `url.original` (`top_values: false` in the catalog: a request target can carry a token), nor for `url.query`, the referrer, `message` and `raw`, which are string and text fields. The readers of a case's statistics are its members while it is active or closed, who read the same values in its events. No admin route carries statistics.

**The search API** (`src/Api/Endpoints/SearchEndpoints.cs`, `src/Query/SearchPlan.cs`). Four routes under a case, each for any member while the case is active or closed (409 otherwise), each running as the query account with the route's case as its whole allowed list.

| Route | Answer |
| --- | --- |
| `POST /api/v1/cases/{id}/search` | a stream of events (`text/event-stream`); with a `cursor`, the next page |
| `GET /api/v1/cases/{id}/search/export?format=csv\|json&query=...` | the result as a file |
| `POST /api/v1/cases/{id}/sql` | the raw-SQL tab: one table, at most 10,000 rows, with `truncated` |
| `GET /api/v1/cases/{id}/sql/export?format=csv\|json&sql=...` | the raw result as a file |

*The request.* `query` (the query language, at most 8,000 characters), `from` and `to` (the picker, in the time grammar), `tz`, `cursor`. **The display zone is UTC unless the request names another** (an IANA id or an offset; an unknown one is 400). A `from` or `to` that is not a time is 400 `bad_request` with the time grammar's message, on the search and on its export. Without a range the search covers the case's recorded span, and a case without one answers an empty result. Limits, page sizes and settings are the server's (`Urlog:Query`): a member of the body the route does not know is refused, so none can be sent.

*The stream.* Every event is one JSON object that names its kind. `meta` is first and is sent before any statement has answered: the resolved range and zone, the kind of result, the columns, the transpiler's warnings and resolved fields, and the case's span with `undated_events` and `future_events`, the events a default range leaves out. Then, for a listing, `histogram`, `page` and `counts`, **each as soon as it is ready, in any order**: the three statements run at once and none waits for another. An aggregation is one `table` instead, pivoted for a timechart. **Its rows come in a total order**: after the keys of `sort`, if any, the by fields and then the aggregate columns, so two groups with equal counts never change places between runs, in the stream and in an export. The search API asks the transpiler for this (`TranspileOptions.TotalOrder`); `urlog query` gets the statement as it was. A table of more than 10,000 rows is cut there and says so: `truncated` is true and `total_rows` is the number of rows the result has. `done` ends the stream; `error` ends it instead when a statement failed, with a code.

- `histogram`: events per bucket and severity over the search's filter, the span chosen as the smallest of 1s 5s 10s 30s 1m 5m 10m 30m 1h 3h 6h 12h 1d 1w 4w that gives at most 300 buckets, cut by the timechart's rule (a day or more on the display zone's calendar).
- `page`: 200 events with every catalog column, `extras`, `raw` and `raw.valid_utf8` (1 when the stored line is valid UTF-8, 0 when the text sent for it holds a replacement character for bytes that are not), so expanding a row asks nothing more; `next`, the cursor of the following page, or null at the end; `capped` when the paging limit was reached. Instants are UTC with a `Z` in every answer. The zone decides snapping, times written without an offset and day buckets, never how a time is written.
- `counts`: the exact total, and the ten most frequent values of each field that has top values in the case's field statistics, from one statement (`GROUP BY GROUPING SETS`). A row without a value in a field is no value of it. When the search narrows nothing, covers the whole span, and the case has no event outside it and a current set of statistics, the stored statistics are these counts already: the event says `"source": "field_stats"` and no statement runs.

*The cursor* is opaque: the range, the zone and the clock the first request resolved, a binding to the case and the query text, the key of the last row sent, and the number of rows before it. The order of a listing is its `sort` keys, then `ts`, `file_id`, `file_offset`, all descending for the default listing. **A visible row is the only one with its file and offset**, since the view shows one generation of a file and a parser writes one row per record, so the order is total: no two rows compare equal whatever their times. The next page is the rows strictly after the last key in that order, written out key by key because the directions of a `sort` differ. A row is before the boundary or after it, never both and never neither, so a walk has no duplicate and no gap, also across pages that split a run of equal times (`tests/Security/SearchApiTests` walks 600 rows that share 200 instants, three files to an instant, 50 to a page). The range is the first request's, so `-24h` and `now` do not move between pages. What it does not promise: a file committed during a walk adds rows, and those that sort before the boundary are not met. The cursor is not signed, because it grants nothing: every row it reaches is one the caller may read by narrowing the range. A cursor for another case or text is 400. A listing is paged to 10,000 events; the page that reaches the limit says so, and a cursor that claims to stand past it is refused with the advice to narrow the search or export.

*The newest-first listing* is read through a time window. The sort key is `(case_id, host, ts)` and the view tests every row against its file's generation, so `ORDER BY ts DESC LIMIT` over a case reads the case. A statement bounded to the newest stretch of time reads one part and about a granule a host. Measured on the development box, quiet, 2026-11-18, the query account over HTTP, 20 warm runs, 200 rows with all columns, p50 / p95 in ms:

| Statement | 25.2 M rows | 100.8 M rows |
| --- | --- | --- |
| the whole range, no window | 1,802 / 1,853 | 8,306 / 8,479 |
| the keys alone over the whole range | 270 / 302 | 1,152 / 1,184 |
| a window of 8 pages of events at the case's density | 77 / 81 | 59 / 62, a miss: 104 rows |

The first window is as long as 32 pages of events take at the case's recorded density (events over span, from the metadata store), which lies between the third and the fourth row of the table and is one statement at both sizes; for a later page it is as long as the window that found the page before. A full page from a window is the page. A window that returns fewer rows is tried again longer, by what the rows it found say is needed and at least 16 times, three windows at most; after that the time of the page's oldest row is read from the three key columns alone and the rows are read from there (83 + 103 ms at 25 M rows for a filter with nothing recent, where the statement over the whole range takes 803). A window that finds nothing costs 12 to 14 ms. A listing with a `sort` is one statement over the range. The mark is p95 at or under 100 ms at 25 M rows and at most twice that at 100 M; the built code measures 55 and 83 ms (below).

Two things the same measurement showed. On the bare table the whole-range listing takes 87 ms; through the view it takes 1,802 ms: the cost is the view's generation filter, which reads `file_id` and `parse_generation` of every row and loses the lazy read of the wide columns. The sort is a small part of it. The view is the security boundary and is unchanged; the window works around the cost for listings, and other query shapes are not measured for it. A projection ordered by time (key columns and `_part_offset`) was built on a copy and rejected: the planner of 26.8 does not read it for the listing (72 ms with it, 70 ms without, on the bare table), it adds 21 % on disk (309 MiB on 1.44 GiB) and 6 % to an insert of the case.

The histogram over a whole case, read from the events, is a read of every row's time and severity: 355 ms at 25 M rows, 1,439 ms at 100 M, by the same line about 14 s at a billion. **A search that narrows nothing is answered from the stored histogram** (ClickHouse schema, Stored histogram) through `IStoredHistogram`, for the whole span and for any other range, when every parsed file of the case has its stored minutes. One statement: the whole minutes inside the range are summed from `case_histogram_v` into the search's buckets by the bucket expression of the live histogram, and the part of a minute at either end of a range that does not end on a minute is counted from `events_v`, a read of about a granule a host, joined to the first by `UNION ALL`. The stored rows are minutes in UTC; a span of a day or more is cut on the display zone's calendar at read time, over the minute as over an event's time, which gives the same days wherever the zone's offset is a whole number of minutes. The answer is the live histogram's, bucket for bucket (`tests/Security/StoredHistogramTests` compares the two for six spans, four zones with four changes of the clocks, and six ranges, over a case with a superseded and an uncommitted generation, undated rows and a row dated years ahead). The event says `"source": "stored"` or `"query"`. The events are read instead when the search narrows anything, when the chosen span is under a minute (a range under five hours), when a file of the case was parsed before the histogram was kept, and when the stored read fails, which is logged. The stored rows have no host (ClickHouse schema, Stored histogram): a timeline per host, or a search filtered only by host answered from stored rows, needs a design and a measurement of its own.

The interior is the cost, and inside it the grouping into the search's buckets is the larger part (34 to 42 ms with no filter at all) and the generation filter the smaller (21 to 24 ms with no grouping). *The bytes of a line.* Every answer above decodes a line as UTF-8 and writes U+FFFD for a byte that is not, so two different lines can arrive as the same text. `GET /api/v1/cases/{id}/files/{fileId}/events/{offset}/raw?ts=...&host=...` answers the stored bytes of one event's line, for any member of the case, through `events_v` as the query account like every search. The caller gives the event's time and host from the row it holds, so the read stands on the sort key `(case_id, host, ts)`; without them the request is 400, so the route cannot be used to walk a case. The answer is the bytes themselves, `application/octet-stream` with `Content-Disposition: attachment`, the SHA-256 of what is sent in `X-Urlog-Raw-Sha256`, and `nosniff` like every answer; no parameter or header of the request changes the type, so no browser renders them. One query slot. The audit row is a query row with `language: bytes`, `request: raw`, the file and the offset, the byte count and the SHA-256 of the bytes, and none of the bytes. For a UTF-16 file the stored line is the transcoding the parser read, which is what the route answers. The interface shows the bytes as a hex dump and offers them as a file; it never decodes them into the page.

*Export.* **An export of events is evidence.** A listing without `table` exports `ts, host, program, severity, source_ip, message` and then `file_id, file_offset, raw`: every row says where in the evidence it came from and carries its line. `columns=brief` gives the first six alone; a query that names its columns with `table` gets exactly those; the audit row says which (`columns: evidence | brief | table`). `GET .../search/export/files` (same `query`, `from`, `to`, `tz`, `format`) lists the files those rows came from: `file_id, name, host, size, sha256, rows`, counted over exactly the rows the export of the same request sends (its order, its limit), with the record of each file read from this case alone. It is audited as its own kind of request (`request: export_files`) with the bytes and their hash like any export. An aggregation has no such list (400). **Two exports of one search are the same bytes.** A listing is exported in its whole order (its `sort` keys, then `ts`, `file_id`, `file_offset`), an aggregation in the total order above, so rows that share a time or a count have one place, and a file cut at the limit is cut at the same row every time. **A listing is exported in two steps, so its sort never holds the columns of every matching row.** Sorting a whole case with `raw` in the row passed the query account's memory limit at 12.6 M events. The first step takes what the export reads (each file with a matching row, its visible generation and its count, which also gives the row count of the headers) and, when the result is longer than the limit, sorts the keys alone to find the row the file ends on. The second step reads the rows up to and including that key in the same order, from those files at those generations, so a file committed between the steps adds no row. A file of the result that is parsed again or removed while the export runs would take rows away, so after the last row the files are taken again and compared: on a difference the download is broken off and the audit row says `failed` with the reason. The files export of the same request carries the same `sha256` of the query text, `from`, `to` and `tz` in its audit row, so the two rows can be matched. The three aggregates that choose among rows are fixed inside a cell as well (`values`, `earliest` and `latest`, above). The query's own statement orders a listing by time alone; the first measured export showed what that means, two files of the same size whose rows with equal times stood in different places. **A raw SQL export has the order its text gives it. A text without a total order is not reproducible, and the tool adds none**: the raw tab runs what the analyst wrote. One row at a time from the event store's reader into the response's pipe, flushed every 64 KB: the memory in use is one row and the pipe's buffer whatever the length, and a slow download slows the read. At most 1,000,000 rows, counted by the API (`max_result_rows` with `break` cuts at a block boundary and may pass more). For a listing one `count()` runs first, so `X-Urlog-Rows` and `X-Urlog-Truncated: true` say before the first byte that a file is cut. CSV is RFC 4180 with a header row; JSON is one object a line. When a column is a field the catalog marks `sensitive`, the file starts with a line that names them (`# sensitive fields: a, b`, or `{"sensitive_fields": [...]}`); without one there is no such line. **A `values(f)` cell is cut to its 100 values in an export as in the stream.** Before the first byte one statement asks which `values` columns hold a group over the cap, over the rows the file will carry, and the file then says so at its start: a line `# values capped: a cell with 100 values in these columns may stand for more: a, b` in CSV, a member `values_capped` of the first record in JSON (the record that also carries `sensitive_fields`). No such column, no line. The statement runs the aggregation a second time, which only an export with `values` pays. **Every other cell is written as it is stored.** An export is evidence, and a cell that begins with `=`, `+`, `-` or `@` is attacker-controlled text that a spreadsheet may run as a formula: the caller who wants it defused asks with `formula_guard=true` (CSV only), which puts an apostrophe before such a cell and says in the first line of the file that cells were altered. JSON is never altered. A failure after the first byte aborts the connection, since a broken download says more than a file that ends early. **The export hashes its bytes as it writes them**, and its audit row says what left the server: `rows`, `bytes`, `sent_sha256` (the SHA-256 of those bytes), `cut` (the result was longer than the limit) and `complete`. A file in someone's hands is matched to its row by its hash. An export its client left, or whose read failed, records the rows, the bytes and the hash of what was written up to that point with `complete: false`. The query text of an export is in its URL, so a proxy's access log holds it and is as sensitive as the audit log.

## Security

Per-case sharing is only real if the raw-SQL tab cannot read other cases. Every control below applies to transpiled and raw queries alike.

**Query path**

1. The backend queries ClickHouse as a dedicated read-only user `urlog_query`: `readonly=2` (settings may be sent, data and DDL may not), `allow_ddl=0`, and exactly three grants, `SELECT` on the views `events_v`, `field_stats_v` and `case_histogram_v` (ADR 0001). A users.xml user with a `<grants>` block has nothing else: no `SELECT` on `events`, `file_generation`, `field_stats` or `case_histogram`, no `dictGet`, no table-function sources (`url`, `file`, `s3`, `remote`, … are refused for want of `READ ON URL`/`FILE`/…), no `CREATE TEMPORARY TABLE`, `system.*` only what every user reads (`system.one`, `system.settings`; `system.tables` lists the three relations). `tests/Security/GrantTests.cs` pins the list.
2. Every query, transpiled or raw, runs against a plain view `events_v` whose definition filters `case_id IN getSetting('SQL_allowed_cases')` and the current `parse_generation`; the backend sends the allowed-case list as a per-query custom setting (`custom_settings_prefixes = SQL_`), never by rewriting the analyst's SQL. A parameterised view was rejected: `FROM events_v` in the raw tab must work unchanged. **Measured on 26.8.36.3 (ADR 0001):** the mechanism holds (`[1]` sees case 1 only, `[1,2]` both, `[]` and an absent setting nothing; a case outside the list is invisible however it is named, through SPL and raw `FROM events_v`), partition pruning on `case_id` survives the view (the `has(..., case_id)` folds to a constant set in the plan). A view without a `SQL SECURITY` clause runs as the invoker on 26.8 and would need the query user to hold `SELECT` on `events`, so `events_v` is created `SQL SECURITY DEFINER DEFINER = CURRENT_USER` (migration 0005); the migrator's admin account is its definer and must stay. The row-policy fallback was measured and not taken: it loses to an inline `SETTINGS` clause exactly as the view does, and a `READONLY` constraint on the setting refuses the per-request parameter too (452), which would force one ClickHouse user per analyst. **Transport (ADR 0003):** the query path uses `ClickHouse.Driver`'s HTTP client, with `SQL_allowed_cases` as a per-request setting parameter; the insert path uses the TCP client. The TCP client drops out-of-band custom settings (ADR 0002), and a session-scoped `SET` is rejected as the isolation mechanism because a pooled connection would leak the setting between users. The SQL text is never rewritten. The isolation tests proved both halves: the gate rejects a user `SETTINGS` clause on both paths, and with the gate bypassed in a harness an inline `SETTINGS SQL_allowed_cases = '[1,2,3]'` on a request that carried `[1]` returns every case (600 of 600 seeded rows). With `readonly=2` the server does not stop it, so the gate is mandatory, not defence in depth. **The field statistics are behind the same mechanism.** `field_stats` is a plain table keyed by case that holds every case's most frequent values, so the query account has no grant on it and the gate refuses its name. It reads `field_stats_v` (migration 0008): the same filter on `SQL_allowed_cases`, the same definer clause, and for each case the newest set only. The fields endpoint sends the route's case as the whole list and names the case in its text as well, and its reader refuses a result that holds a row of another case. `tests/Security/FieldStatsTests` asks the view for a case outside the list in five ways (zero rows each), and reads the table with the gate out of the way (497). **The stored histogram is behind it too.** `case_histogram` holds every case's counts per minute and severity, so the query account has no grant on it and the gate refuses its name; it reads `case_histogram_v` (migration 0009), which has the filter on `SQL_allowed_cases`, the definer clause and the generation filter of `events_v`, and shows neither the file nor the generation of a bucket. `tests/Security/StoredHistogramTests` asks it for a case outside the list in the same five ways.
3. Every query text, transpiled or raw, is parsed with ClickHouse's own parser (`EXPLAIN AST`, run as the same read-only user, so nothing executes) and rejected by `src/Query/RawSqlGate.cs` unless the tree is a plain SELECT (with CTEs, subqueries, unions) whose root carries no `FORMAT`, `INTO OUTFILE` or `SETTINGS`; any `SETTINGS` clause anywhere, any table function, any qualified name (`system.tables`, `default.events_v`), any relation the migrations create other than `events_v`, `field_stats_v` and `case_histogram_v` (in `FROM`, `JOIN`, a subquery or the right side of `IN`), more than 8 nested SELECTs, an empty text or one over 16 KB are refused; a text the server cannot parse (comment-split keywords, multi-statements) is refused too. The dump does not name CTEs, so an unknown unqualified name is let through to the server's `UNKNOWN_TABLE`; the grants cover the rest, and a test asserts the gate's relation list against `system.tables`. One extra round trip per query, a few milliseconds.
4. Per-query limits: `max_execution_time` 60 s, `max_memory_usage` 4 GB, `max_result_rows` 1 M, as `readonly` constraints of the profile: measured unraisable (and unlowerable) by request parameter and by inline `SETTINGS` alike (452); `readonly` and `allow_ddl` cannot be switched off (164, 392). **The API bounds what it runs itself** (`QuerySlots`): the query account is one for all analysts, so the server's `max_concurrent_queries_for_user` cannot tell them apart. A request takes one slot for each statement it may have in flight before its first byte (three for a search: histogram, page and counts; one for a page, an aggregation, a raw query or an export) and gives them back when it ends. A user has **4** (a search and one more request beside it) and all users together **12** (three analysts at their limit, so one user at the limit never takes a slot another is entitled to; `tests/Api.Tests` hold one user there and start another's search). A request that cannot have its slots within a second is answered 429 with `Retry-After`; a stream that has begun holds what it needs and is never answered 429. A user runs one export at a time. **`max_concurrent_queries_for_user` 16** on the profile, with the same `readonly` constraint, is the server's own stop above the API's total, with room for the reads outside the slots (the field statistics, `urlog query` on the box); the host refuses a total at or above it (measured: unraisable by request parameter and inline `SETTINGS` (452), and with sixteen queries in flight the next is refused with 202 `TOO_MANY_SIMULTANEOUS_QUERIES`, which the API passes on as 429). **`cancel_http_readonly_queries_on_client_close` 1** on the same profile, readonly as well: a query whose HTTP client has closed the connection is stopped instead of running to the 60 s limit (the server's default is off; `GrantTests` pins the value and the behaviour).
5. Test: every scenario in the validation suite also runs as an unauthorised user and must return zero events, through both the transpiled path and the raw-SQL tab (`tests/Security/UnauthorisedUserTests.cs`; the whole of `tests/Security` runs from `tools/pre-merge.ps1` against the pinned image with the deployed users.d/config.d files).

**Write path.** The backend process holds no admin credential at runtime. Inserts, the re-parse protocol, case deletion and the per-case field statistics run as a dedicated `urlog_ingest` user with exactly: `INSERT` on `events`; `INSERT`, `SELECT` and `ALTER DELETE` on `file_generation` (the delete removes the generation rows of a purged case's files; measured on 26.8.36.3, the same privilege passes `ALTER TABLE file_generation DROP PARTITION tuple()`, which empties the table and hides every file until a runner starts and writes the rows back from SQLite, and the account could already hide any file by inserting generation 0); `SELECT` on `store_identity` (the store's identity, which every writer compares with the metadata file's before it writes; its one row is written by the admin account); `ALTER DELETE` on `events` (the lightweight delete of a file's rows, and the partition drop of case delete and purge; the drop carries `SETTINGS max_partition_size_to_drop = 0`, because the server refuses to drop a partition above 50 GB by default and takes the statement's value over its own, measured both ways); `SELECT` on `events` **only** for the two reads that live in `Core/Ingest` and always carry their own case predicate: the field-statistics task, with the view's generation filter, and the fill of the stored histogram, which reads one generation of one file (the two places outside `events_v` the table is read); `SELECT` on the `system` tables the inserter and the job runner watch (`parts`, `merges`, `mutations`, and `disks` for the ingest watermark: disk names with free and total bytes, nothing else); `INSERT` and `ALTER DELETE` on `field_stats` (a case's statistics are removed when the case is deleted or purged and when they are recomputed; the account cannot read the table); `INSERT` and `ALTER DELETE` on `case_histogram` (the fill, the delete of a file's superseded and failed generations, and the partition drop at archive and purge; the account cannot read that table either). No DDL, nothing on `events_v`, no table functions; a profile without the read-only constraints but with `max_memory_usage` bounded (4 GB).

*One grant is wider than intended because the server (26.8.36.3) has nothing narrower.* There is no `ALTER DROP PARTITION` privilege (`GRANT ALTER DROP PARTITION` is a syntax error): `ALTER TABLE ... DROP PARTITION` is checked against `ALTER DELETE`, so one grant covers the lightweight delete and the partition drop, and the same grant covers `DETACH PARTITION` (with `INSERT`, `ATTACH PARTITION` too). **`ALTER DELETE` lets the ingest account delete any rows of `events`** (and of `field_stats` and `case_histogram`, which are derived from `events`: the first is recomputed by the statistics task, the second written again by a re-parse): every file's, every case's, by lightweight delete, by a heavy `ALTER ... DELETE` mutation or by dropping or detaching partitions. A grant cannot say "one file" or "one case", so the account that inserts can also erase. What it cannot do is touch the schema (`CREATE`, `DROP`, `TRUNCATE`, `RENAME`, `ALTER` of columns, TTL or `UPDATE`, `OPTIMIZE` are refused, 497), delete from `file_generation` or `schema_migrations`, read `events_v`, `schema_migrations`, `field_stats` or `system.query_log`/`processes`/`users`/`grants`, `dictGet`, manage users or grants, or reach outside the server through a table function. **The recovery from a lost or wrongly deleted case is the evidence, not ClickHouse:** the original files under intake are never modified and their SHA-256 is in SQLite, so the rows are rebuilt by re-parsing them (a new generation per file); ClickHouse holds nothing that cannot be derived again. The `allow_ddl` setting stays on for this profile, because `ALTER ... DROP PARTITION` counts as DDL to it: "no DDL" is the absence of grants, not the setting. The read of `events` is composed in one place, `Core/Ingest/CaseScopedEventsQuery`, whose every text carries `case_id = <n>` as its first predicate; a test scans `src/` for any other `SELECT` on the table.

*Credentials.* `urlog` and the API take one credential per role: ingest (`--user`/`--password`, `URLOG_CH_USER`/`URLOG_CH_PASSWORD`, `urlog_ingest`), query (`--query-user`/`--query-password`, `URLOG_CH_QUERY_USER`/`URLOG_CH_QUERY_PASSWORD`, `urlog_query`) and admin (`--admin-user`/`--admin-password`, `URLOG_CH_ADMIN_USER`/`URLOG_CH_ADMIN_PASSWORD`), the last used by `urlog migrate`, `urlog pair` and `urlog bench query --cold` only and absent from the backend's configuration by default. Every CLI command prints the account it connected as (the name, never the password). `urlog ingest` does not migrate and cannot: a missing schema is an error that names `urlog migrate`. The users.d file in the repository is the development stack's: its `::/0` networks and its passwords equal to the account names are stubs; production restricts both backend accounts to the backend's network and takes the passwords from secrets. Migrations stay on the admin account (`urlog migrate`, a one-shot service in Compose), which is also the definer of `events_v` and must never be dropped or renamed (ADR 0001). `tests/Security/GrantTests` pins both accounts.

**Users and roles (`src/Api`, `src/Core/Auth`, `src/Core/Metadata`).** Local accounts only: the first admin is created on the box by `urlog user create --admin`, every later account by an admin through `POST /api/v1/users` or the CLI. Roles: `admin` (manage users, the admin case routes, purge) and `analyst`. A case is owned by its creator and shared with named users as `owner`, `rw` or `ro` (`case_members`; a case always keeps one owner). No SSO, LDAP or OIDC in v1.

*Passwords.* Argon2id (Konscious.Security.Cryptography.Argon2, managed, no native artifact) at **64 MiB, t = 3, p = 1**, 16-byte salt, 32-byte tag, stored as the PHC string the reference `argon2` tool writes (`$argon2id$v=19$m=65536,t=3,p=1$...`); the parameters are constants pinned by a test, and a stored hash below them is re-hashed at the next successful login; 12 to 256 characters, no composition rules (NIST SP 800-63B); never logged, never in a response. A user changes their own password with `POST /api/v1/auth/password`: the current password is verified like a login, outside any transaction; the new one is held to the same policy and may not be the current one; every other session of the user ends and the one that made the change goes on; `user_password_change` holds the number of sessions ended and neither password. The change is refused when the stored hash is no longer the one that was verified, so a reset by an administrator that arrives in between is not undone. The route is counted by the login throttle of the caller's address, wrong and right attempts alike: a session in the wrong hands gets no faster a guess at the password than the login page gives. A name that does not exist is verified against a dummy hash so the response time does not say whether the account exists (asserted within 50 %).

*Sessions.* A `sessions` row keyed by the SHA-256 of the cookie token (the file never yields a usable session); cookie `urlog_session` `HttpOnly`, `Secure`, `SameSite=Strict`, no `Max-Age`; idle 8 h and absolute 24 h (configurable); the role and the lock state are read from `users` on every request, so a role change or a lockout applies at once; lockout, role change and password reset end the user's sessions; logout deletes the row. Every request whose method is not GET/HEAD/OPTIONS repeats the session's CSRF token in `X-CSRF-Token` (a middleware, so no endpoint can opt out; 403 `csrf`), with `SameSite=Strict` as the first lock.

*Login.* A per-address throttle first (5 attempts per minute by default; the 6th is 429 with `Retry-After` before the user row is read or any hash computed; **process memory, reset on every restart**, which is harmless because the durable control, the lockout counter, is in SQLite; the first refusal of a window writes one `login_throttled` row, later refusals none). The client address is the socket's; `X-Forwarded-For` is believed only from a proxy listed in `Urlog:Http:TrustedProxies` (the Compose deployment lists the proxy container). Then the Argon2 verify outside any transaction, then one `BEGIN IMMEDIATE` transaction with the outcome's rows: `login` with the session row, or `login_failed` (`reason` unknown_user | wrong_password | locked). **Ten consecutive failures lock the account for 15 minutes** (both configurable; `user_lockout`); an admin ends it earlier with `POST /api/v1/users/{id}/unlock` or `urlog user unlock` (`user_unlock`, the break-glass for a locked sole admin); the expiry writes no row and the next attempt counts from zero. One generic 401 for unknown, wrong and locked.

*Case ACL.* Enforced by a middleware that runs before parameter binding and validation on every endpoint carrying `RequireCaseRole(owner | rw | ro)`: no membership, or a case in a hidden state (`soft_deleted`, `purging`, `purged`), is **404 with the same body as an unknown id**; a membership below the required role is **403**. One route reaches a hidden case: `POST /api/v1/cases/{id}/restore` admits a case that is `soft_deleted` (never one that is `purging`) for a member who holds the owner role, and answers everyone else the same 404, a member of another role included, so the route does not say that a deleted case exists. The owner finds such a case under `GET /api/v1/cases?state=deleted`, which lists the caller's own soft-deleted cases with the day their purge falls due. A startup assertion refuses to start the host if any route under `/api/v1/cases/{id}` lacks the requirement, any route under `/api/v1` other than login allows anonymous callers, or any `/api/v1/users` or `/api/v1/admin` route lacks the admin policy; the route theory in `tests/Api.Tests` enumerates the live route table, so every later endpoint is covered the day it is mapped. Admin has no implicit case access: `/api/v1/cases/{id}/...` answers 404 to an admin without membership; the admin's explicit, audited path is `GET /api/v1/admin/cases` (metadata and the member list of every case, never events or field statistics) and `/api/v1/admin/cases/{id}/members`, whose rows (`case_share`, `case_role_change`, `case_unshare`, `by_admin: true`) target the case and so appear in its own trail where the owner sees them. These routes carry a case id with the admin policy in place of a membership requirement (the startup assertion demands the policy and refuses a membership requirement there), and a non-admin is answered 404 on every `/api/v1/admin/` route as if it did not exist; `/api/v1/users` stays a visible admin function and answers 403. `SQL_allowed_cases` for a search, an export, a raw query and the field statistics is the one case of the request's route, set after the membership check and for that request alone. A member of several cases reads one case a request, in the raw tab too; a search across cases is a later feature.

**Audit log.** An append-only, hash-chained table in the metadata store, with a genesis row and `schema_version` (`src/Core/Audit`).

| Field | Content |
| --- | --- |
| `seq` | assigned by the writer, never by the database: the last seq + 1, so no gap on rollback |
| `ts_utc` | UTC, truncated to whole microseconds |
| `actor`, `actor_id` | user name, OS user or `system`; the user id when there is one |
| `action` | lowercase snake_case verb from the list below |
| `target_type`, `target_id` | `case`, `file`, `user`, `query` or `backup`, and the row id at the time (a plain number: the trail outlives its target) |
| `details_json` | canonical JSON; names the target (`case_name`; a file's `sha256`, `original_name`, `size`; `user_name`) because a SQLite id can be reused |
| `prev_hash`, `hash` | `hash = SHA-256(prev_hash ‖ canonical JSON of the row without hash)`, 64 lowercase hex; the genesis row's `prev_hash` is 64 zeros |
| `schema_version` | the audit format (1), on the genesis row only |

**Canonical JSON** (`CanonicalJson`, pinned by vectors and three known-answer rows computed with Python's `json` and `hashlib`, so a runtime upgrade cannot move a hash): object keys in ordinal UTF-16 order (RFC 8785's), every key present with `null` written out, no whitespace, UTF-8; strings escape only the double quote, the backslash and the controls below U+0020 (the short forms for backspace, tab, newline, form feed and carriage return, otherwise `\u00xx` in lowercase hex), everything else raw; integers only (no floats: durations are milliseconds, sizes bytes); timestamps `yyyy-MM-ddTHH:mm:ss.ffffffZ`. The hash input is the previous hash as ASCII hex followed by the row object of ten keys, with `details_json` embedded as the stored string, never re-parsed: a verifier needs no JSON parser and any changed byte breaks the link.

**Append-only in the store.** Three SQLite triggers (migration `AuditTriggers`): `UPDATE` and `DELETE` abort; an `INSERT` whose `seq` is not the last seq + 1 or whose `prev_hash` is not the last row's hash aborts, so a fork is an immediate error. The EF entity has no setters. The triggers stop application bugs; against someone holding the file, the chain and the backups are the control.

**Same transaction.** Every audited change runs as: `AuditChain.BeginTransactionAsync` (`BEGIN IMMEDIATE` on SQLite, serializable on Postgres), the change saved, `IAuditWriter.AppendAsync`, commit. The writer refuses to run outside a transaction. A failure before the commit, the audit append included, leaves neither the change nor the row. `CaseOperations` and `FileOperations` are the model.

Actions: `genesis`; `store_identity_created`, `store_paired`; `login`, `logout`, `login_failed`; `case_create`, `case_share`, `case_unshare`, `case_close`, `case_reopen`, `case_archive` (the commit of an archive: its directory, the SHA-256 and size of the tar and of the manifest, the file and byte counts, and every file that was missing or changed with the recorded and the found hash and size), `case_archive_complete` (partitions dropped, files removed), `case_archive_failed` (an archive given up, with the reason), `case_reimport` (the case closed again: files parsed, files whose parse failed, files whose row count differs from the manifest's), `case_reimport_refused` (the reason, and the file when one can be named), `job_cancelled` (a job held since the close, cancelled by the archive of its case; `file_intake`, `file_duplicate`, `file_rejected` (a refused file, on the case), `file_override` (the override before and after, what the detector had found, the re-parse it queued), `file_update` (a person changed a file's host, zone or year: each with its old and new value), `file_bulk_host` and `file_bulk_override` (one call changed many files: on the case, with the selection, the new value, the digest of the selection and every changed file with its SHA-256), `file_bulk_redetect` and `file_redetect` (detection asked for again, and its result per file), `host_create`, `host_update`, `host_merge` (on the case, with the host's id and name), `job_retry` (a person queued the work of a failed or cancelled job again; `job_cancelled` is also written when a person cancels a job), `file_reparse`, `file_expand_rerun` (an archive queued again with limits given by hand), `input_truncated`, `integrity_ok`, `integrity_mismatch`; `user_create`, `user_role_change`, `user_lockout`, `user_unlock`, `user_password_reset`, `user_password_change` (a user's own); `login_throttled` (the first refusal of a throttle window); `case_role_change` (a member's role; `case_share` and `case_unshare` are add and remove); `query` (one row for every request that carried a query text, written when the request ends, target the case: the `text` and the `sha256` of its UTF-8 bytes, `language` spl or sql, `request` search, page or export, the resolved `from`, `to` and `tz`, `first_row` for a page, `outcome` ok, invalid, rejected, failed, timed_out, abandoned or busy with its `reason`, `duration_ms`, and `rows`, the number of rows sent; for an export also `bytes`, `sent_sha256`, `cut` and `complete`, null on every other request. It never holds a result: no cell, no value, no bucket. A client that closes the connection is `abandoned`: its reads are cancelled, the query account's profile stops the statement on the server (`tests/Security/SearchApiTests` leaves a two-second raw query and asserts it is gone from `system.processes` within 1.5 s), and the row is written all the same. A row that cannot be written before the answer fails the request; after a stream it is an error in the log); `backup`; `ingest_paused` and `ingest_resumed` (the disk watermark stopped or released the queue: the volume, its free and total bytes, the mark, the number of queued jobs; actor `system`, no target). The runner's other job transitions write no row: the `jobs` table is their record. **Verification.** `urlog verify-audit --db <file>` walks the chain read-only and reports the first broken link with a reason (`gap`, `genesis`, `no_genesis`, `prev_hash`, `hash`, `malformed`): a deleted row 5,000 is reported at 5,001, a changed byte in row 7 at 7. It then prints the head on one line, `audit head seq N hash H`. **The chain cannot show that rows were cut off its end**; only a head recorded outside the machine can. Analysts copy the head line into the case notebook or ticket and pass it back as `--expect N:H`; `--backup <file>` checks a backup's head the same way. Each case's trail is exported as JSONL (one canonical line per row, hash included, from the latest `case_create` of that id) for the archive manifest.

## Consistency across SQLite and ClickHouse

No transaction spans the two stores, so every cross-store operation is either restartable from scratch or idempotent step by step. The ingest queue lives in SQLite (single process, workers as threads), never in ClickHouse.

| Operation | Rule |
| --- | --- |
| Parse | job states are under Job runner below; a crash mid-file restarts the whole file: the attempt's rows are deleted, its stored histogram with them, and the file is parsed again under a new generation. Chunk-level resume is deliberately not built |
| Re-parse | insert the new generation first; set `current` in the files table only after the insert completes and the hash agrees, then write `file_generation`. A crash leaves the old generation visible, never a mix |
| Settings changed during a parse | the claim stamps the job with the file's `settings_version`; a job that ends, done or failed, under an older value than the file then has queues the next parse of the file in its own last transaction. No file has a second job waiting beside a running one, and a parse under old settings is never the last |
| Expand | the container is verified and listed before anything is written; members are recorded in batches with a resume point on the container, so a crash repeats the listing and writes only what is missing. It writes no events, so nothing in the event store depends on it |
| Archive | the archive is written and read back from disk against its manifest before anything else; then (a) one transaction marks the case `archived`, (b) the archive is hashed again against that commit and the partitions are dropped, (c) the files are removed. Nothing is dropped or removed before (a). Before (a) a stop is answered by building again; after it the steps only go forward (Archive below) |
| Re-import | the archive is held to the audit chain, to its manifest and to the file records, and extracted into a staging folder; only then are the files put back and the parses queued. Any doubt refuses the whole of it and restores nothing (Re-import below) |
| Purge | a backup of the metadata file, then (a) mark `purging` in metadata, (b) drop partitions, the stored histogram with them, delete the field statistics and the generation rows, (c) delete files, (d) delete metadata. Every step idempotent; a startup reconciler resumes any case still `purging` (Purge below) |
| Watcher | reconciles the intake directory against the files table on startup |
| Integrity sweep | every stored file is read again and compared with its intake record, nightly, only while no job runs; each result is an audit row and a changed or missing file is quarantined (Integrity sweep below) |
| Any write | the metadata file's store identity is compared with the event store's first; a pair that does not match writes nothing (Store identity below) |

The UI shows a real per-file progress bar from chunk counters, which are advisory only and not used for resume.

**Job runner** (`src/Core/Jobs`, `JobOperations` in `src/Core/Metadata`). One runner per metadata file: it holds `<db>.runner.lock` open without sharing, and the operating system releases it however the process ends. A starting runner tries for the lock for 5 s before it reports another runner: under load the handle of a killed runner was seen still held when its exit was reported. The backend hosts the runner (`Urlog:Ingest`); `urlog worker` is the same runner for a command-line deployment, and whichever starts second is refused. *Claim:* one `BEGIN IMMEDIATE` transaction takes the oldest `queued` job whose case is `active` and has no job in `parsing`, so a case never has two jobs running and jobs of different cases may. The times on a job row (`created_at`, `started_at`, `finished_at`) are read from the clock after the operation holds the write lock, so their order is the order of the transactions: a claim that waited for the lock behind the commit of the case's previous job never starts before that job finished. `MaxConcurrentJobs` defaults to 1. Measured on the dev box with two 1 GiB nginx files in two cases, three alternating passes: one after the other 13.2 to 14.4 s in total at 2.0 GB peak working set; together 11.8 and 12.3 s at 3.7 GB, and in the third pass one of the two jobs failed with ClickHouse's `MEMORY_LIMIT_EXCEEDED` (241) at the server's 6.5 GiB cap. Together is about 12 % faster when it fits and does not always fit, so the default is 1 and the setting is there for a box with the memory. *Job states:* `queued → parsing → done | failed`, `parsing → queued` on a stop (a graceful stop keeps the attempt number, an unclean one raises it and the third fails the job, so a file that takes the process down cannot loop), `queued → cancelled`. A terminal job never changes; a retry or a re-parse is a new row. *One job:* the evidence file is opened read-only and read once; SHA-256 runs over the raw bytes on the reader thread, the rows go to ClickHouse under the attempt's own generation, and after the last acknowledgement the digest and the size are compared with the intake record. Equal: the stored histogram of the attempt is written from its rows (ClickHouse schema, Stored histogram), then SQLite (job `done`, `files.parse_generation`, `files.histogram_generation`), then `file_generation` in ClickHouse, then the delete of the generations below, in `events` and in the histogram. The attempt's generation is one above every generation the file's jobs have used and above the value `file_generation` holds for the id, which covers a file id SQLite has reused after a purge and a metadata file restored from a backup older than the event store (the purge itself clearing its files' generation rows is the case lifecycle's). A refusal of the event store for memory (ClickHouse 241) is treated as passing: the attempt's rows are deleted, the job is queued again as the next attempt, and no slot claims anything for 30 s (`MemoryLimitBackoff`); the attempt cap ends it. A final write that finds SQLite locked is retried for `CommitBusyTimeout` (60 s; the store's own busy timeout is 5 s), and past that the runner stops with the job in `parsing`. The retry is `BusyRetry` in `src/Core/Metadata`, one policy for every write that must not be lost to a lock: the write is started again from its beginning, in a new transaction, until the time is up. The record of a web upload uses it as well (Intake, Web upload). The busy timeout itself has no setting; a test that stages a locked file passes a shorter one to the store's constructor, in whole seconds, which is the provider's unit. Every failure path deletes the attempt's rows in ClickHouse first and writes SQLite last. The failure reason on the job row is the pipeline's reported exception with its chunk context, verbatim. *Startup, in order:* the lock; the event store answering the ingest account (until it does nothing is claimed); the metadata file's store identity compared with the store's (Store identity below; a mismatch ends the start with nothing written to either); the metadata migrations; every job found in `parsing` cleaned and requeued; `file_generation` written from SQLite wherever the two differ (for the files SQLite has a committed generation for); cases in `purging` (the purge's own steps come with the case lifecycle; until then such a case is logged); the watermark; then claiming. *Watermark:* ingest pauses while any watched volume (the metadata directory, the evidence root, the event store's disks from `system.disks`) has less free space than the larger of 20 GB and 10 % of the volume; every queued job's message says which volume and by how much, and `ingest_paused` / `ingest_resumed` are in the chain. *Progress:* chunks read and parsed, acknowledged rows and bytes go to the job row every 2 s; the acknowledged-chunk figure is the acknowledged share of the parsed chunks, since the store acknowledges INSERTs. *Measured (dev box, 1 GiB nginx, same day, alternating, three each):* `urlog ingest` 177.2 / 199.4 / 194.9 MB/s, median 194.9; through the runner 175.5 / 176.1 / 177.9, median 176.1, which is 90.4 % of direct. The difference is the hash. **The hash costs more inside the read than alone:** 2.50 to 2.65 s per GiB against the 2.2 to 2.3 s measured for it alone, because the reader thread shares the cores with eight parsers, four writers and ClickHouse, where the separate pass had them to itself (2.25 s the same day). In wall time it costs the job about 0.6 s per GiB. Accepted as measured; the lever not built is a hash thread of its own behind a bounded hand-off. `EndToEnd.PipelineNginx1G` with the progress counters: 414.3 ms against 410.6 ms before, 0.00 B/row.

**Store identity.** A metadata file belongs to one event store. Case ids and file ids are allocated by the metadata file, `events` is partitioned by case id and `file_generation` is keyed by file id alone, so a metadata file pointed at the store of another deployment writes over files it has never seen. A job's commit raises the generation of a file id the store already holds, and the startup sync writes `file_generation` from SQLite wherever the two differ. Either one hides the other deployment's rows from `events_v` without an error, and a purge would drop its partitions the same way. The pair therefore carries one identity, 128 random bits written as 32 hex characters, in a one-row table `store_identity` on each side (EF migration `StoreIdentity` in the metadata file, migration 0007 in the event store). *The check* (`StoreIdentityGuard`) reads the metadata side on a read-only connection before any migration of the file, reads the store side as the ingest account, and refuses unless both exist and are equal. The message names the file, the server and both values, with `none` for a side that has no identity. *Who runs it, before the first write to either store:* the job runner (after the lock and the event store's answer, before the metadata migrations, the reconcilers and any claim), and `urlog worker`, `enqueue`, `expand` and `case`. A running runner compares again on every watermark tick. When the store at its address has been replaced it claims nothing more, a job in flight stops before its commit and stays in `parsing`, and no delete is sent to the store. `urlog user` and `backup` write the metadata file alone: they require that the file has an identity and do not ask the event store, so the break-glass for a locked administrator works while the store is down. `urlog verify-audit` writes nothing and is never refused: the chain of any metadata file is verifiable, whether it has an identity or predates it. `urlog query` has no metadata file and writes nothing; it is not checked, and the query account has no grant on the table. *The backend* compares before it listens. Until the comparison has passed it answers `GET /api/v1/health` only, to anyone, with 503 and the reason: `waiting_for_event_store` when the store does not answer or has no schema, `store_identity_mismatch` with both values when they differ. Every other route answers 503 without running its handler, the metadata file is not migrated and the hosted runner does not start. The comparison is tried again every 5 s (`Urlog:ClickHouse:RetryInterval`), so a store that comes up later is picked up without a restart. The health body carries the two values and neither a path nor an address; those go to the log. *Where an identity comes from.* `urlog migrate --db <file>` gives a new deployment its identity. When the metadata file has no file record and the event store holds no event row and no `file_generation` row, one value is generated and written to the metadata file, with a `store_identity_created` audit row, and then to the store; a run that stopped between the two is finished by the next one while the store is still empty. Nothing else creates a metadata file: the backend and `urlog user create` refuse a file that has no identity. `migrate` refuses every other combination with both values. *Pairing* (`urlog pair --db <file>`, as the admin account, holding the file's runner lock) is the one way to join a metadata file and a store that already hold data: a deployment from before the identity existed, a metadata file restored from a backup taken before it, a store that was replaced. The store's identity never changes. The metadata file takes it, or, when the store has none, the store gets the metadata file's value or a new one. Before anything is written the command prints what each side holds (cases, file records, committed generations; event rows, `file_generation` rows) and what the next start of a runner would do with the pair: how many committed generations are the same on both sides, how many differ (the sync writes the metadata file's value over the store's), how many have no row in the store, and how many file ids the store holds that the metadata file does not know. It then asks for the identity to be typed back (`--confirm` for a script; without it and without a terminal it refuses). The change and its `store_paired` audit row (the old value, the new value, the server, the counts shown) are one transaction. *Upgrade.* A store and a metadata file from before this rule have no identity. `urlog migrate` adds the empty table to the store and says so, and `urlog pair --db <file>` is run once; for a pair that belongs together its report shows no differing generation. No existing deployment is paired automatically, because a pairing nobody looked at is the mistake the rule is there to stop. A backup carries the identity, so a metadata file restored from a backup taken after pairing matches its store as it is. *`urlog ingest`* keeps no record and takes its ids as arguments. A store without an identity belongs to no metadata file and takes any id. Into a store that has one, `ingest` needs `--store-id` equal to the store's identity, a `--case` at or above the case id floor and a `--file-id` at or above the file id floor. Both floors are 4,611,686,018,427,387,904 (2^62). The metadata file never allocates an id there: triggers on `cases` and on `files` refuse an insert or an update whose id is at or above the floor. A row written without a record therefore cannot land in a recorded case's partitions, where it would show in that case and go with it at a purge, and cannot meet a recorded file's id in `file_generation`. *A scratch metadata file*, for a measurement or an experiment, gets an event store of its own (`tools/scratch-store.ps1`: a second container without a volume, then `migrate --db` on the new file).

**Purge (`LifecycleExecutor` in `src/Core/Lifecycle`).** Carried out by the process that holds the runner lock: the runner's lifecycle loop, the startup reconciler, or `urlog case purge` when no runner is up (with one up, the command records the release and the runner carries it out).

| Step | Does | After a stop here: SQLite / event store / disk |
| --- | --- | --- |
| backup | `VACUUM INTO` and its `backup` row | soft_deleted / everything / everything |
| mark | one transaction: the case becomes `purging`, its queued jobs are cancelled, `case_purge` | purging / everything / everything |
| store | the identity check again, then every partition of the case from `system.parts` is dropped and looked for again, and the case's partition of `case_histogram` after them; the identity check again, then `DELETE FROM field_stats WHERE case_id = n` and the delete of the `file_generation` rows of the case's file ids, read back until none is left | purging / some or nothing / everything |
| files | the case's directory under the evidence root (stored files, `.uploads/`, `web/`), its cache directory and its archives under the archive root | purging / nothing / some or nothing |
| metadata | one transaction: `case_purge_complete`, then every row of the case in `jobs`, `files`, `hosts`, `case_members`, `case_tasks` and `cases` | nothing in any of the three; the audit rows stay |

Before the mark a restore withdraws the purge and nothing was removed. From the mark on it only goes forward: a resume starts again at the store step whatever the last run reached, and each step finds nothing left to do where the earlier run already did it. The executor has no undo and no clean-up of its own on failure, so an exception and a killed process leave the same state and the same resume finishes both. A tick of the lifecycle loop that finds nothing to do only reads: it asks for no write lock and never stands in the way of a job's claim or commit. A purge that fails keeps its task row with the reason and is tried again after a wait that doubles from 30 s to an hour. A stop between the backup and the mark costs one more backup, since the mark names the backup taken immediately before it. The startup sync of `file_generation` leaves out the files of a case in `purging`, so it does not write back what the store step removed. A file that was recorded where it was found, outside the evidence root, is never removed; and a process that was given no evidence root does not delete the records of files stored under one. `evidence_sha256` in `case_purge_complete` is the SHA-256 over the UTF-8 text of the SHA-256 of every file record of the case, sorted by ordinal comparison, each followed by one line feed, so it can be computed again from the backup. After the last step the case id and the file ids can be handed out again, and their generation rows are gone, so the new files start from no row.

**Archive (`LifecycleExecutor`, `ArchiveWriter`, `ArchiveReader`).** The archive root (`Urlog:Lifecycle:ArchiveRoot`, `--archive-root`, `URLOG_ARCHIVE_ROOT`) is apart from the evidence root and the cache root: a start is refused when it is one of them, lies inside one or contains one. An archive is the directory `<archive root>/<case id>/<utc>/` with `evidence.tar.zst`, `audit.jsonl` (the case's trail) and `manifest.json`. The tar holds one regular file per stored file that arrived, named `files/<file id>`, and nothing else: no directory entry, no link, no name or path of the evidence. The manifest lists every entry with the record's SHA-256 and size and the SHA-256 and size of the bytes that went into the tar, every file record of the case with its members, the hosts, the store identity, the head of the audit chain, and the SHA-256 and size of the tar.

| Step | Does | After a stop here: SQLite / event store / disk |
| --- | --- | --- |
| build | what an earlier attempt left is removed; tar, trail and manifest are written into `<utc>.partial`, each stored file read once and hashed as it is written | closed / everything / everything, and a partial directory |
| verify | the manifest and the tar are read from disk: every entry of the tar must be a regular file named `files/<digits>`, listed, there once, with the size and hash the manifest gives, and the tar as a whole must hash as the manifest says; files 0440, directory 0750; the directory gets its name | as build |
| commit | one transaction: the case is still `closed` and no job of it runs; it becomes `archived`; the jobs held since the close are cancelled with a `job_cancelled` row each; `case_archive` | rolled back: as verify. Committed: archived / everything / everything, and the verified archive |
| store | the tar and the manifest are hashed again and compared with the commit; the identity check; the partitions are dropped and looked for again, the stored histogram's with them; the field statistics are deleted. The `file_generation` rows stay, so a re-import's parses are numbered above them | archived / some or nothing / everything |
| files | the case's directory is looked through once more for anything unaccounted for, then emptied; its cache is removed | archived / nothing / some or nothing |
| complete | the task is `done`, `case_archive_complete` | archived / nothing / nothing but the archive |

Before the commit a stop costs the attempt: the next one removes the leftovers and builds again, and after three attempts the archive is given up with `case_archive_failed` and the case stays `closed` and whole. From the commit on a resume starts at the store step. An archive that no longer hashes as it was committed stops there: the task fails with `case_archive_failed`, nothing more is dropped or removed, and it is never re-imported from. A stored file that is not what its record says when the archive reads it is archived as found and flagged: the manifest and `case_archive` carry the recorded and the found SHA-256 and size (or `missing`), the command prints them, and the record is quarantined with `integrity_mismatch`, `check: archive`. A file recorded where it was found, outside the evidence root, goes into the tar and is never removed. An archive reads the whole of the case's evidence and does not wait for the queue as the sweep does, so it competes with a running ingest for the disk; it is asked for by a person and is expected to be.

**Re-import.** The case stays `archived`, and unreadable, until the end.

| Step | Does | After a stop here |
| --- | --- | --- |
| verify | the case's directory is emptied. The manifest's SHA-256 must be the one in the `case_archive` row and on the task; the manifest must be of this case and this store; every entry must agree with its file record in SHA-256 and size and with the record's stored path; every stored path must be a plain path inside the case's directory. Then the tar is walked as at the archive's verify step and each entry is written to `<case dir>/.reimport/<file id>` | archived; a staging folder. The next attempt starts again |
| place | each staged file is moved to the stored path its record has and made read-only. A file recorded outside the evidence root is left where it is when it is still there and still the same; otherwise it goes to `restored/<file id>` and its record is updated at the next step | archived; some files placed. The next attempt starts again from an empty directory |
| queue | one transaction: a re-parse for every record that had a committed parse, the new stored paths, the task moves on | archived; the jobs run |
| close | when no job of the case waits or runs: `archived` to `closed`, `case_reimport` | |

Every name written to disk comes from a file record or is the file id as a number; a name in the tar is only ever compared. A refusal at the verify step removes the staging folder, fails the task, writes `case_reimport_refused` and, when it is about one file, `integrity_mismatch` with `check: reimport` on that file; no record changes and nothing outside the staging folder was written. The runner claims the queued parses although the case is archived, because the re-import's task is under way, and for no other reason. A parse that fails does not hold the case: it is closed and the row lists the file. A row count that differs from the manifest's is listed too and is no refusal, since a newer parser may count differently. The archive stays where it is after a re-import; a purge removes it.

*Measured, not gated.* On the dev box, the 1 GiB nginx fixture as the one stored file of a case, evidence root and archive root on the same volume, three rounds of archive, re-import and parse in a scratch store: the build (one read, SHA-256, tar, zstd level 3, write) took 5.83 to 5.95 s, 180 to 184 MB/s; the read-back with the commit (read, decompress, SHA-256 per entry and over the file) 3.22 to 3.27 s, 328 to 334 MB/s; dropping the partitions and removing the files 0.5 s. The tar was 125.0 MB, 11.6 % of the evidence. The re-import up to the queued jobs (read, decompress, hash, write to the staging folder, move into place) took 3.69 to 3.78 s, 284 to 291 MB/s, of which the placing was 0.07 s. The parse that follows is the ordinary ingest of the file.

**Removing a directory (`GuardedDelete`).** Every recursive removal goes through one check. The path is made absolute and normalised, and it is removed only if it lies strictly under the evidence root, the cache root or the archive root and is not a root itself. Neither the target nor any directory between the root and the target may be a symbolic link or another reparse point: a removal never goes through a link. Inside the tree a link is removed as a link and never entered. A refusal removes nothing.

**Integrity sweep (`IntegritySweep`).** From `Urlog:Lifecycle:SweepAtUtc` (03:00) the runner reads every stored file once, least recently verified first (`files.verified_at`), and `urlog sweep` does the same by hand under the runner lock. It covers the files that arrived, for cases in active, closed and soft_deleted without lifecycle work under way. For an archived case it reads the archive: the tar and the manifest are hashed and compared with what the archive was committed with, the result is an `integrity_ok` or `integrity_mismatch` row on the case with `check: archive`, and a mismatch fails the archive's task, so a re-import is refused before it reads a byte. Archive members are inside their containers and are covered by them; cache copies, unfinished uploads and quarantined files are not read. It does not compete with an ingest for the disk: it reads one file at a time and asks before each file and after every 16 MiB of one whether a slot has a job. While one has, it first writes the results it has, then holds with the file open and its hash state kept, and goes on from the same byte afterwards; a process killed during the hold loses nothing that was already read. The hold begins at the sweep's next question, so it can read up to 16 MiB after a job has started before it holds; from there to the job's end it reads nothing. It stops for a purge that waits. One run reads no file twice, and a run that was stopped goes on with the files whose last result is oldest. A file whose bytes or size differ from the record is quarantined with `integrity_mismatch`; so is one that is gone, unless what is gone is the evidence root or the volume, which says nothing about the file. Its queued jobs are cancelled and no new one is taken. The bytes on disk are not touched. Rows parsed from the file before stay visible, since they were hashed in the read that produced them; the file record carries `quarantined` for the interface to show. A file that cannot be read (permissions, an I/O error) gets no row and is taken first by the next sweep.

**SQLite backup.** The metadata file holds the evidence hashes and the audit chain, so it is backed up with `VACUUM INTO` nightly and immediately before every purge, to a configurable directory, with the backup's own SHA-256 written to the audit log (a `backup` row with path, size and reason) and to a `sha256sum`-format sidecar beside the file (`metadata-<utc>.sqlite.sha256`). A backup is never overwritten, and one whose audit row cannot be written is removed. The backup ends one row before the row that records it; `verify-audit --backup` checks that the live chain still extends it. `urlog backup` is the same path by hand; the nightly schedule is the job runner's, the pre-purge call the lifecycle's. A backup taken before a purge still holds the purged case's records: its files with their hashes, its hosts, its members. That is what the hash of that backup in `case_purge` and `case_purge_complete` points at, and whoever keeps backups keeps what was purged for as long. Losing ClickHouse loses time; losing SQLite loses the proof.

## Cases, hosts, files and jobs API

The routes the case pages of the UI call, all under `/api/v1` and all behind the case ACL (`src/Api/Endpoints`; the operations are in `src/Core/Metadata`). A handler calls one operation as the session's user. The operation checks the case and the version under the write lock, makes the change, queues what the change calls for and writes the audit row, all in one transaction, so a change without its row and a row without its change do not exist (a test fails the audit append under every operation and compares the whole metadata file).

In `soft_deleted` and `purging` every case route answers 404, the restore of a soft-deleted case by its owner excepted. A refusal by state is 409 with the operation's message and leaves no row. A test holds a table of every route that changes a case with its answer in each state, sends each request in each state, and fails when the live route table has a changing route the table lacks.

**Closed and archived.** A closed case is one whose evidence no longer changes, and that covers how it is read as well as what it holds: no host or file of it changes, also where the change would parse nothing. Its members, its lifecycle and the cancel of a job it holds since the close stay open. An archived case takes members, a soft-delete and a re-import.

**What a change re-parses.** A change that alters what a parse of a file would write queues that parse in the same transaction, and nothing else does. For one file: its host, its override, and its zone or year when its source reads times without a zone (`SourceInfo.NaiveTimestamps`). For a host: a rename reaches every file of the host, a zone the files without a zone of their own whose source reads one, a default option the files of the source the option belongs to that set no value of their own for it. A merge reaches none. A file that is never parsed (an artifact without an override, a quarantined file, an archive) is changed and gets no job. A file whose job waits gets no second one, since that job reads the settings when it is claimed. A file whose job runs is followed up when that job ends (Consistency).

**Cost first.** A change that would have files parsed again answers first with what it costs and changes nothing: the number of files and their stored bytes (`reparse`), with `applied: false`. The same request with `?confirm=true` makes the change and answers 202. That holds for a host's name, zone and default options and for every bulk change. A change to one file is made at once. A host change that reaches no file is made without the confirmation. The audit row of the change carries the count and the bytes.

**Versions.** A host and a file carry a version that every change a person makes raises (`hosts.version`, `files.settings_version`). The job runner's own writes (progress, a commit, counts) do not touch it, so a commit never makes a person's edit stale. A response carries the version, a single read also as `ETag`, and a change sends the version it was made against in `If-Match`. Without the header the change is refused (428); with an older version it is refused (412) and the answer names the current one. The comparison is inside the operation's transaction, so of two people who change one record from the same view one is told. A bulk change names its selection the same way: the unconfirmed call answers a digest (SHA-256 over one line per selected file, id and version), the confirmation sends it in `If-Match`, and a selection that differs under the lock is 412 with nothing changed. A case's state needs no version: every transition reads the case under the lock and the loser is told both states.

**Bulk changes.** `assign-host` selects by a path template over the archive path, or the name of a file that arrived alone, in the syntax of the host patterns without `{host}` (never a regular expression). `override` selects by extension (behind compression and rotation suffixes), detected source and kind, optionally layout and host. One call touches at most 1,000 files. A larger selection is refused (422) with its size, and a caller walks it with `after_id` and `limit`, each step its own transaction and row. The row is on the case and lists every changed file as id and SHA-256 (about 90 bytes each, under 100 KB at the limit), with the selection as given, the new value, the digest and the files the selection matched and the change left as they were, counted by reason. Nothing is partial: the checks, the changes, the jobs and the row are one transaction, and a refusal or a failed append leaves no file changed and no job queued. What can differ per file afterwards is its parse, which is a job with a state and a reason of its own. Measured on the development box (Release): 1,000 files given a host with 1,000 parses queued in one call took 870 to 936 ms from the request to the commit, during which other writers of the metadata file wait as they do behind any transaction.

**An override, as a person sees it.** The answer to the request is 202 with the file and the job. The file shows the override as set, `reparse` with the job and its state, and `settings_applied: false`; its rows, rejects, span and generation are those of the committed parse, and every search still reads that parse. While the job runs its counters move and searches go on reading the old rows. At the commit the file shows the new generation with its counts and span and `settings_applied: true`, and `file_reparse` is on the trail. A search that began before the commit ends on the old rows and one that began after reads only the new ones, since `events_v` builds its set once a query; the stored histogram changes with the same statement, and the statistics of the case show `pending` until their task has run. When the job fails the old rows stay visible, the file stays `parsed`, the job says why, the override stays on the record with `settings_applied: false`, and the next step is a retry or another override.

**Jobs.** The list and the single read show a job's state, its counters with the size of its file for a progress bar, and its message: the failure reason word for word as the pipeline reported it, or why the job waits. A read-write member cancels a job that waits, also the one a closed case holds, and queues the work of a failed or cancelled job again as a new job. Only the newest job of a file can be run again. Both are rows on the file.

**Dashboard.** `GET /cases/{id}/dashboard` is what the case page shows above its file list: the files by state and by kind with their row and reject totals, the count of each flag that wants a person's eye (unassigned, host inferred, quarantined, truncated, spans a DST change, undated, future-dated, year assumed, detection stale, re-parse pending, no stored histogram), the queue and the job that runs, every host with its files, rows, rejects and span, the span of the case, the state of its statistics, the lifecycle work under way and disk use. The file list is no part of it: 10,000 file records are megabytes of JSON, and the files route pages them. `files.rows` and `files.rejects` are the sums of the file records. `usage.store_rows` is what `system.parts` holds for the partitions of the case, every generation and every row a delete has only masked, so it can be above the files' total, and the two are named apart.

*What it costs.* The counts are one grouped statement over the file records of the case (by host, state and kind, with a conditional sum for each flag), the jobs of the case by state through the index on `(case_id, state)`, and reads by key of the hosts, the statistics row and the lifecycle task. No statement reads the event store. Measured on the development box (Release, three runs of 50 requests each over HTTP through the session and the ACL, after one unmeasured request) on a case of 10,000 file records, 10,000 jobs and 50 hosts: p50 47.8 to 48.0 ms, p95 50.7 to 52.8 ms, a body of 13.5 KB. Reading a narrow projection of every record into the process and adding up there measures p50 85 to 88 ms and p95 103 to 107 ms on the same case, which is why the store adds up. On Linux (the WSL clone, same build) the same case measures p50 24.7 to 25.8 ms and p95 29.2 to 36.5 ms. Disk use is apart from those figures. It walks the directories of the case, one entry for each file that arrived (archive members cost none), and asks `system.parts` as the ingest account for the partitions of the route's case after the membership check; it is measured at most once in 30 s for a case, kept in memory with the time it was taken, and when the event store does not answer the dashboard carries the counts with `usage: null` and says so. The walk over 10,000 stored files measures p50 7.0 to 7.3 ms on the development box and 17.3 to 18.3 ms on Linux (20 passes after one unmeasured, three runs). It takes an entry for a link by the attributes the listing of its directory gave and skips it; asking the file system about every entry a second time, as a removal does before it deletes, costs 2.3 s for the same 10,000 files on Windows, and a count neither reads through an entry nor removes one. Nothing about who may see a case is kept between requests.

## v1 user interface

Splunk's Search & Reporting core, which is where analysts spend most of their time, plus three DFIR-specific additions that cost little and separate an incident tool from a Splunk clone.

| Element | Behaviour |
| --- | --- |
| Search bar | CodeMirror 6, single line auto-grow, SPL highlighting, autocomplete, inline error marks |
| Time picker | absolute, relative, presets; bounded to the case span |
| Histogram | uPlot, severity-stacked, brush-to-zoom |
| Field sidebar | top-10 values per field with counts; click = AND filter, alt-click = NOT |
| Event table | virtualised, fixed row height, expand for raw and parsed fields, column picker, cursor-paginated |
| Saved searches | per case |
| Export | CSV/JSON of the current result set, streamed, capped at 1 M rows |
| Case dashboard | hosts, files with SHA-256 and detection result, ingest progress and reject counts, disk use |
| Bookmarks and tags | mark an event, add a note; appears on the histogram and in a timeline view: the artifact handed to the report writer |
| Pivot on value | right-click any field value → search it across all hosts in the case |
| Timezone toggle | UTC / source / local, shown explicitly in the header; "assumed" badge when the source TZ was defaulted |

Results stream as events: `meta` first, then the histogram, the first page and the counts each as soon as it is ready, so the page fills progressively (Query language, The search API).

**The web client (`web/`).** Every colour, font, size of type, space and radius is a design token in `web/src/styles/tokens.css`, and a lint rule refuses a literal anywhere else; light and dark are two sets of colour values under the same names. The system's setting decides the theme until the user chooses one, and the choice stays in that browser. The two typefaces (IBM Plex Sans for the interface, JetBrains Mono for data; both SIL Open Font License 1.1) are served by the instance with their licence texts beside them, and the page loads nothing from another host. The logo, the favicon and the loading screen are drawn from one set of geometry constants; with reduced motion the loading mark stands still. The client's types come from `web/openapi.json`, the description of the routes that the host builds from its live route table: no route serves it, a backend test compares the tracked file with what the host builds, and the client's type check then fails wherever a changed route or record was used. A production build goes to the backend's web root and the backend serves it; an address under `/api` that names no route is answered 401 or 404, never with the page. A refusal (a wrong sign-in, a case that is not shared, a role that is too low, a wait the server asks for) is shown as a plain notice in the server's words where it has any; the error colours are for failures. A request answered 401 anywhere ends the session in the browser and returns to sign-in, which leads back to the same address; after a sign-out it leads to the case list. **Uploads in the browser** (`web/src/upload`). The client speaks the server's part of tus itself (create, HEAD, PATCH, DELETE) and keeps the rules of the table under Web upload as states: once the server holds every byte nothing more is sent, whether the last chunk's request answered, answered 503 `upload-pending`, or lost its answer; a HEAD answered 423 is "verifying"; after a cut the server's offset decides where to go on; every chunk of 16 MB carries its SHA-256, and a chunk answered 460 is sent again from where it began. Two uploads run at a time and the rest wait, since each finished upload is hashed by its last request and parsed by a queue of one. A reload of the page keeps the address of each unfinished upload in the tab's own storage and loses the file itself, which a page cannot open again: the upload is shown with the offset the server holds and goes on when the same file (name, size and time of change) is chosen again; one whose bytes had all arrived needs no file and goes on to its result. Closing or reloading the tab while bytes have still to be sent asks first. A sign-out forgets the tab's uploads. The page of a case reads the dashboard and the file list, asks the dashboard again every two seconds while a job waits or runs, a run of the statistics is pending or an upload of the tab is at work, and reads the file list again when the dashboard's counts change.
**The search page** (`web/src/search`, `web/src/pages/Search.tsx`). The address holds the query, the range, the display zone, up to three extra columns and the open event, and the page runs what the address holds; an address without a query searches the whole case. The stream of `POST /search` is read with `fetch` and cut into events by the client, since `EventSource` sends no body. A new search ends the one before, and nothing that still arrives for an ended search is drawn. Timeline, events and count are each drawn when their own event arrives. While a search loads, the results before it stay on the page, dimmed and named by the query that produced them; after a refusal they stay undimmed. The server's warnings and a syntax error are marked in the query at the offset and length the server gives, and listed under it. A 429 is waited out by `Retry-After` and sent again up to five times, shown as a neutral notice, and is an error only after that. A stream that ends with an `error` event, or without its closing event, keeps the parts that arrived, marks them as from an incomplete run and says of each missing part why it is missing. The list asks for the next page by the cursor as the reader nears its end, draws only the rows in view at one fixed height, and says so where the server capped it; an aggregation is one table with its cut and its capped rows said above it. The timeline is drawn with uPlot, stacked into four series by severity; a drag, or the arrow keys with the chart in focus, select a stretch of time, which becomes the range of the address. An event opens from the row the list already holds and asks the server only for the name and hash of its file. The query box is CodeMirror without a grammar: what is wrong with a query is said by the server alone. The detail leaves out a 0 in a field the catalog marks `zero_is_absent` and shows any other 0 as the value it is. An event whose row says `raw.valid_utf8` 0 says that its text holds a replacement for bytes that were not UTF-8, so neither the text nor Copy is the exact line; a line that holds U+FFFD of its own is not taken for one. The detail fetches the bytes of the line on request, shows the first 4 KiB as hex (hex digits, dots and printable ASCII only) with the server's SHA-256, and saves them as a file. A piece of a long line says "part 2 of 3 of one line that begins at offset N", leads to a search of its parts, and saves the whole line as one file by fetching the bytes of each part in the order of the file (up to 200 parts). **The field sidebar** lists the fields of `GET /fields` that have events, with their count and estimated number of values, and the keys outside the catalog thirty at a time. Under an open field stand the ten most frequent values of the search on the page, each with "only" and "exclude": from the `counts` event, or from the case's statistics when the event says `field_stats`. A field without stored top values, and a key outside the catalog, is asked for when it is opened, by a search of its own (`<the search part of the query> | stats count by <field> | sort -count | head 10`) that takes one query slot and waits out a 429 like any search; a name that cannot be written as a word of the query language says that its values cannot be asked for. **Completion** offers the catalog's names and aliases, the keys outside the catalog that are words, and after a pipe the verbs the server names; it completes the word at the cursor and knows no grammar. **Export** is the search of the address, as CSV or JSON lines, in the evidence form unless "brief columns" is ticked, with the formula guard off unless ticked; the files of the result are an export of their own in the same menu. Where the browser has `showSaveFilePicker` the reader chooses the file first and the answer is piped into it as it arrives; elsewhere the page takes the answer into a blob and hands that to the browser as a download. Either way the page reads the answer itself, so a refusal is shown as one (429: an export of the user is already running), the row count and the cut at the server's limit come from `X-Urlog-Rows` and `X-Urlog-Truncated`, and a download that breaks off or is cancelled leaves no file under the chosen name. Measured for the 1,000,000-row limit on the development box (2026-11-25, headless Chromium, one run each): a CSV of 141 MB raised the browser's working set by about 200 MB written as it arrives and 233 MB held; JSON lines of 216 MB by 242 MB and 323 MB; the page's own heap stayed near 12 MB in all four. Holding costs 1.5 to 1.65 times the file (measured), so the page holds a file only when its estimate of the size (the rows the search matches, up to the limit, times the columns and the average line of the loaded rows) is at most 300 MB, which keeps the cost under 500 MB; above that a browser without a file picker gets a plain download link and the page says that it cannot show progress or a refusal.

**Text out of a log** is written by whoever attacked or was attacked, and the interface treats every raw line, field name and field value as hostile. Such text reaches the document only as text nodes, through one module (`web/src/search/inert.tsx`); nothing is built from a string, no address in it becomes a link, and a lint rule refuses `dangerouslySetInnerHTML`, `innerHTML` and their kin anywhere in `web/`. Control characters, the C1 block, direction marks and overrides, zero-width characters and half surrogate pairs are drawn as marked placeholders with the code point in the title and are never applied; the direction of the text is set by the page. Copying takes the string as the server sent it. A table cell draws at most 400 characters and the detail draws a long value 20,000 characters at a time and the fields of an event 200 at a time, each with what is cut said and a way to the rest, so a line of a megabyte or an event of thousands of fields costs what a person can read. A value that cannot be typed into a query (one with such a character, or longer than 500 characters) is not offered as a filter. **Content policy.** Every answer of the host carries `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` (`ApiHost.ContentSecurityPolicy`): no inline script or style, no `eval`, no other origin, no framing. Beside it, on every answer: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (the address of a search holds the query), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, and a `Permissions-Policy` that grants no browser feature to anyone except writing to the clipboard to the page itself, which its Copy buttons need. Every answer under `/api` carries `Cache-Control: no-store`. The host sets no `Strict-Transport-Security`: it listens behind a proxy, and that header is the proxy's, set in the deployment. The client is built to fit it. CodeMirror would add a style element to the document, so the editor lives in a shadow tree, where its styles are a constructed sheet; uPlot ships a stylesheet file and sets sizes through the style object; dialogs use the browser's `dialog` element and the user menu is not modal, because the scroll lock of the modal primitives injects a style element.

## Validation

Parser fixtures prove parsing; scenario tests prove the tool finds things. Both run in CI against ClickHouse in Docker.

**Scenario test** = a public dataset + a list of SPL queries + the expected answers, e.g. "which account brute-forced web-01 and when did it first succeed". Each scenario also runs as an unauthorised user and must return zero rows.

**Datasets** are fetched by script and never vendored into the repository:

| Dataset | Covers |
| --- | --- |

| Boss of the SOC | multi-source incident data, where licensing allows |
| [SecRepo](https://www.secrepo.com/) | nginx, syslog and other samples |

Scenario results ("finds X in dataset Y in Z seconds") double as demo material and release notes.

## Throughput proof and cut list

**The throughput proof (four weeks)** comes before any UI exists. No auth, web UI or watcher.

- [x] BenchmarkDotNet harness with fixed-seed 1 GB nginx and 1 GB syslog fixtures, disk read rate reported separately (`DiskRead`: 214 to 505 ms for the 1 GiB fixture on the dev box, depending on the page cache; reported, not gated)
- [x] C# nginx and syslog tokenisers at ≥ 50 MB/s per core (nginx 1,273 MB/s; syslog 1,390 MB/s, both 0 B/row on the dev box)
- [x] ClickHouse schema and Native insert path at ≥ 1 M rows/s in Docker, block size parameterised (1.0-1.08 M rows/s in the bench with the index on at 4 writers, 0.7 M rows/s sustained over five minutes on the dev box, where ClickHouse is CPU-bound on inserts plus merges)
- [x] CLI ingests a 1 GB nginx file (\~5 M events) end to end (`urlog ingest`: 4,809,713 rows at a median 194.9 MB/s on the dev box)
- [x] `src_ip=X | stats count by url.path` transpiled and answered at p95 < 500 ms warm, < 2 s cold, on the reference box (measured on the dev box, 25 M rows, 20 runs: p95 201 ms warm, 186 ms with the server caches dropped; the OS page cache stays, so a cold start in the full sense is not measured)

The alternative considered for the tokeniser budget was parsers and ingest in Rust with the API in C#. Measured on the dev box (i9-9900KF, .NET 10.0.14, one core, 0 B/row): nginx 1,273 MB/s (5.7 M rows/s), syslog 1,390 MB/s (10.1 M rows/s), 25× and 28× the 50 MB/s floor. **The Rust alternative is not taken.** C# with `Span<byte>`, `SearchValues<byte>` and `Utf8Parser` is the parser language.

**Cut order under schedule pressure**, first to go first:

1. `timechart` and charts beyond the histogram
2. Saved searches
3. Postfix and journald parsers (syslog, nginx, EVTX stay)
4. Archive state (close and delete stay)
5. SFTP watcher (web upload only)
6. Bookmarks and tags

**Never cut:** benchmark harness, hashing and audit, query security, tokeniser SLO, scenario tests, format-override UI.
